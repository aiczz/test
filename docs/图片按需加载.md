# 食材和菜谱图片按需加载

FoodPhoto 和 DishPhoto 共用 LazyPhoto。进入可视区域后请求 `POST /api/images/resolve`，
离屏内容不请求图片；同名卡片与详情共用请求和短期状态缓存。

解析顺序：服务器已缓存的图片 → 仓库现有配图 → 后台生成缺图。
生成时卡片保留本地图片或占位，约每 5 秒查询状态，完成后替换成服务器图片。
断网、未配置生图服务和服务错误均不影响食材/菜谱的文字与操作。
Logo、装饰插图和头像保持原有加载方式。

## 后端配置

新增两个状态表 `image_cache`、`image_generation_budget`，包括 compact 模式在内均在
启动时自动创建，不修改导入的菜谱和食材原始表。图片文件存入 `IMAGE_STORAGE_DIR`，
数据库保存文件名、来源、状态、尝试次数和生成模型；数据库不存图片二进制。

`back/.env.example` 列出了全部配置。默认关闭付费生成，已有图片照常通过 API 返回。
启用时配置 `IMAGE_GENERATION_ENABLED=true`、`IMAGE_GENERATION_URL`（完整地址）、
`IMAGE_API_KEY`、`IMAGE_MODEL`。这是独立于对话模型的生图服务。

生图适配契约：向完整端点 POST `{model,prompt,n:1,size}`，Bearer 认证；
响应为 `{data:[{b64_json:"..."}]}` 或 `{data:[{url:"https://..."}]}`。
返回 URL 时必须在 `IMAGE_DOWNLOAD_HOSTS` 配置精确的 CDN 域名，下载不携带 API 密钥。
不支持该契约的服务需要更换适配器 `_provider`。未配置密钥时不会发生真实模型调用。

公开用户可读取已有照片；生成须登录且名称必须存在于内容库。
全局最多两个执行线程、八个排队及执行任务；同一内容通过数据库原子占用去重。
默认每日最多 40 次生成尝试、每项最多 3 次，失败间隔 300 秒。
服务器异常退出的任务在租期结束后由再次访问触发恢复。多进程共用数据库和图片目录；
每日额度是数据库级的，执行线程数是每进程的。大规模部署可替换为独立任务队列。

## 部署和已有图片

所有图片地址位于 `/api/images/{key}/content`，沿用现有 `/api` 反向代理，手机使用
已配置的 API_BASE，不需要增加静态资源代理规则。文件响应有一天 HTTP 缓存。
部署时 `IMAGE_ASSET_DIR` 指向已有图片目录，例如 Web 构建产物下的
`assets/assets/images`。应持久化生成目录，并将目录和数据库一起备份。

已有图片名清单是 `back/app/data/image_assets.json`，来源为前端两张图片映射表，
更新图库后运行 `python scripts/sync_image_assets.py`（在 back 目录）。
前端仍保留本地资源作为离线回退，因此此次不减少 APK 体积。
生成图片标注“AI 示意图”，不表示原菜谱实拍，也不改变配料或营养事实。

## 验证

后端测试使用临时 SQLite、模拟生图响应和临时图片目录，不会产生真实生图费用。
配置真实端点后仍需验证该服务的协议和手机到后端的连接。
