## 一、值得肯定的地方（建议保留并写进汇报）

这几条是真的好，队友独立想到了正确设计，不要改：

1. **「先过滤 → 再排序 → 最后生成」的顺序正确**。而且第 1 条明确写了「**AI 生成后再做一次安全校验**」—— 这就是我们方案里的 Critic 否决机制，方向完全一致。
2. **「外部接口失败时使用最近一次缓存，并在界面标注『参考数据』」** —— 这与我们 4.6 节的"本地快照 + 置信度标注"是同一个设计，队友独立想到了，说明工程判断力在线。
3. **「没有市场数据也不阻塞基于库存的菜谱推荐」** —— 降级思路专业，避免了把系统做成"接口挂了就全废"。
4. **「每日上下文独立保存，避免修改今天的计划影响长期偏好」** —— 这是很好的数据建模意识，正对应我们 4.2 节区分的**短期上下文**与**长期偏好**。
5. **市场数据适配器写了 `normalize / cache / fallback` 三层** —— 与我们 4.5 节的管道分层（抓取→归一化→折算→服务）结构一致。
6. **「用户主动加入的候选食材标记为『必须使用』」** —— 把用户意图提升为硬约束，产品细节到位。
7. **数据对象设计基本齐全**：`User / FoodRule / DailyContext / IngredientCandidate / DishRecommendation / DailyMenu / CookingHistory / Feedback`，且以 `user_id` 为归属键，思路正确。

## 二、三个致命缺口（必须补，否则拿不到算法分）

### 缺口 1：没有优化求解层 —— 整套是"打分制"而非"约束优化" ⚠️ 最严重

架构图里写的引擎是：

```
推荐与约束引擎：hard filter → scoring → generation
```

**这是打分排序，不是求解。** 打分制有三个硬伤：

| 硬伤 | 说明 |
|---|---|
| **表达不了跨菜品、跨天的耦合约束** | 预算总量（Σ 成本 ≤ 300 元）、7 天钠累计、食材复用（买一把葱分配给 4 道菜）、保质期（周三到期的菠菜必须周三前用掉）—— 这些都不是"给单个菜打分"能表达的 |
| **贪心、不保证可行** | 逐菜打分取 Top-K，无法保证全局最优，也无法保证解满足全部约束 |
| **无法处理约束冲突** | 当"预算 300"与"营养达标"不可兼得时，打分只能各自加权；做不到"在预算内最大化营养"，更说不出"哪条约束最紧" |

**最要命的后果**：把"营养约束"降级成"打分项"之后，**有高血压成员的家庭可能被推出一道钠超标的菜** —— 因为超标只是扣分，不是禁止。这对竞赛是硬伤：评委一句"你这能保证钠不超标吗"就答不上来。

**改法**：在 AI 组合菜品之后插一层 **CP-SAT / MILP 求解器**，把营养、预算、时间、厨具、保质期作为**真正的硬约束**。LLM 只负责生成候选和解释，判定权交给求解器。

```
现状：  候选食材 → [AI 打分排序] → 菜单
改后：  候选食材 → [LLM 生成候选] → [CP-SAT 求解] → [Critic 校验] → 菜单
                                      ↑ 硬约束在这里
```

### 缺口 2：没有"买什么菜"的采购规划 —— 产品定位缺了半边

把整份文档的工作流走一遍：

```
开启今日计划 → 读规则与历史 → 采集上下文 → 查市场数据
→ 合并过滤候选食材 → 用户选择基础食材 → AI 组合菜肴
→ 确认菜单？ → 生成做法并写入历史
```

**从头到尾没有采购环节。** 具体缺：

- ❌ 买**多少**（份量 → 采购量换算）
- ❌ 花**多少钱**（总价、预算控制）
- ❌ 按货架/菜场**分类**的购物清单
- ❌ **浪费控制**（临期食材优先消耗）

现在用户是**手动**"一键加入基础食材"，系统只做**推荐候选食材**。所以这个产品的实际形态是**「菜谱推荐 App」**，不是**「买菜做菜助手」** —— 名字里有"买菜"，流程里却没有采购决策。

**改法**：补上我们方案的 **Stage 3 采购批量优化**：给定菜单 → 求解最小化「成本 + 浪费」的采购量，服从保质期与先入先出，输出分类购物清单。这也是**最贴"买菜"这个卖点、最容易讲出故事**的算法点。

### 缺口 3：完全没有评测方案

全文档无 benchmark、无指标、无 baseline、无消融实验。竞赛方案缺这一块等于**没有证据**。

**改法**：直接采用 `项目方案.md` 第 6 章（13 项指标 / 7 层 baseline / A1–A8 消融 / 多周仿真 / 学习曲线）。

## 三、必须修正的错误与风险

### 3.1 架构图与流程图互相矛盾（答辩会被追问）

| | 流程图 | 架构图 |
|---|---|---|
| **市场数据在哪一步获取** | 「采集今日上下文」→ 【**查询外部数据**】→ 合并过滤候选食材 | 「**推荐与约束引擎** → 市场数据适配器」 |

同一件事，流程图放在**候选过滤阶段**，架构图挂在**推荐引擎**上。而且架构图里 **「每日计划服务」完全没有连到「市场数据适配器」或 EXTERNAL 区** —— 按架构图，每日计划服务根本拿不到市场数据，但流程图要求它在过滤候选时用到。

**改法**：统一为「市场数据在**候选食材过滤阶段**由每日计划服务调用适配器」。推荐引擎不再直连适配器。

### 3.2 架构图缺三条关键连线

1. **「账户与规则服务」没有连「偏好与历史库」** —— 但 `FoodRule`（allergies / dislikes）明明存在那个库里（DB 标签写了 `rules / daily_history / feedback`）。规则数据从哪来？必须补线。
2. **「推荐与约束引擎」没有连「偏好与历史库」** —— 但流程图要求它做「历史降权」，硬过滤还要用过敏规则。它拿不到这些数据。
3. **「账户与规则服务」没有回程箭头**到移动端。

> 架构图是答辩时最容易被逐条追问的图，**每条连线都要能解释**。建议重画时逐条自检："这个服务的数据从哪个库来？"

### 3.3 「供货量」「地方特色」接口并不存在

架构图 EXTERNAL 区写的是「时令 / 均价 / **供货** / 地方特色」接口。实际情况（已核实，见 `项目方案.md` 5.1）：

| 字段 | 现实 |
|---|---|
| 均价 | ✅ **有官方公开数据** —— 农业农村部批发价 + 省市公共数据开放平台农贸市场零售价 |
| 时令 | ⚠️ **不需要外部接口**，用月份 + 食材表**自己算**即可 |
| 供货量 | ❌ **没有对应的公开数据源** —— 可能是设想出来的 |
| 地方特色 | ⚠️ **不需要外部接口**，用手工维护的「地域→菜系」映射表即可（本地查表，零网络） |

**风险**：答辩时评委问"你这个供货接口是哪个"，会答不上来。

**改法**：把 EXTERNAL 区明确改成「**官方农产品价格数据接口**」，删掉"供货量"，"时令"和"地方特色"改为**内建静态表**（不占外部依赖，断网可用）。

### 3.4 「轻量登录：用户名/手机号 + 简单口令」—— 建议直接删掉

三个理由：

1. **合规风险**：手机号属个人敏感信息，自建账号体系涉及《个人信息保护法》，加密存储、注销权等都要处理 —— 竞赛项目不值当背这个
2. **演示摩擦**：答辩现场还要输密码，白白浪费宝贵的演示时间
3. **没必要**：记忆功能只需要"一套数据归属一个用户"，不需要真实身份

**改法**：改为**浏览器本地匿名 `user_id`（UUID）+ 可选家庭档案**。零合规风险、零演示摩擦，且正好与我们已加的 `PRIVACY.md` 一致。

### 3.5 「生成做法并写入历史」的时机有逻辑漏洞

流程图在**用户确认菜单后立即**写入历史。但 §04 的 `Feedback` 又提到「**实际做了**」。

问题：如果 `CookingHistory` 记的是**计划**，那「近 3–7 天重复则降权」会把**计划了但根本没做**的菜也算进去 → 去重逻辑失真。

**改法**：拆成两张表 ——
- `PlannedMenu`：计划（确认菜单时写入）
- `CookedLog`：实际完成（用户点"实际做了"时写入）
- **降权/去重只读 `CookedLog`**

## 四、与已冻结方案的两处直接冲突（需团队立刻拍板）⚠️

这两条如果不解决，队友可能正在往错误方向做。

### 冲突 1：**移动端形态 —— 队友图上是「移动端 App」，我们已决定 PWA**

- 队友架构图 CLIENT 区写的是 **「移动端 App」**
- `项目方案.md` 1.4 节【冻结】：**放弃 Flutter / RN 原生开发，改为响应式 Web + PWA**

**这是最紧急的一条。** 我们的判断是：原生双端会吃掉 7–10 天（打包/签名/上架/双端调试），而对"AI 算法精英大赛"几乎不加分。省下的时间投到求解器和评测上，收益高一个数量级。

如果队友已经按原生 App 开工，**必须马上对齐**，否则会白做。如果团队决定保留原生 App，那**算法和评测必须相应缩减** —— 这是一个此消彼长的取舍，不能说"都要"。

### 冲突 2：**只有「今日」单日闭环，没有周规划 → 算法深度会大幅缩水**

全流程是单日闭环（"每日计划"、"今日菜单"）。但单日视图会导致三个能力无法实现：

| 做不了 | 因为 |
|---|---|
| **预算优化** | 预算是**周**概念（300 元/周），单日无法规划 |
| **浪费优化** | 浪费来自**跨天**库存，单日没有库存演化 |
| **学习曲线** | 偏好学习的效果要**多周**才能观测（见 6.3） |

**改法**：升级为**周菜单规划**，单日只是周计划里的一个切片（用户可逐日微调）。这一改动同时解锁了预算优化、浪费最小化、学习曲线三个亮点。
