# AI核心算法优化记录

日期：2026年10月15日。

本轮重点为需求识别、模型故障处理和可复现评估。

## 需求识别与连续对话

- 明确的食材、菜谱、库存和连续追问由本地规则先识别，避免每次都先请求模型分类。
- 明确的新推荐对象优先于上一轮话题。例如菜谱之后说“换一批食材”，切换到食材；食材之后说“再来三道菜”，切换到菜谱。
- 修改人数、时间、少盐要求时保留当前推荐类型。
- 推荐数量作为独立会话条件，默认3项，支持1至10道菜或种食材。识别“5道”“五道”“5到菜谱”等表达，区分人数和时间；“换一批”保留数量，“改成两道”更新数量。候选召回、整餐选择、模型提示和最终卡片使用同一数量，候选不足时明确告知，不放宽忌口等条件凑数。
- 会话保存最近推荐食材和菜谱的标识，以及最近8条用户/助手消息（每条最多1000字符）。前端已有的可见推荐也可作为引用输入，支持“用这些食材推荐菜谱”“用上面的”；食材引用不要求先写入库存。普通问答带上有限历史和推荐对象，开始新会话、账号切换继续使用原有隔离机制。记录随当前浏览器会话状态在本机保存，不是跨设备的永久记忆。
- “推荐一下”“安排一下”等未说明对象的请求先询问食材还是菜谱，返回needs_clarification，不生成卡片，也不调用模型。
- 知识问题和普通话题走直接问答；询问“低钠是什么意思”不会自动开启低钠条件。用户明确取消忌口的操作仍然有效。
- 只有规则无法明确处理的话题才尝试模型分类，分类等待配置默认为3秒。模型分类不是独立评测过的语义理解系统，长句、否定和多意图表达仍需继续扩充评估集。

## 模型调用与故障冷却

- 明确推荐请求省去分类调用，正常路径只调用一次模型完成选择和说明；未配置模型时继续使用算法结果。
- 已有成功响应缓存继续使用，容量128项、默认300秒。
- 模型繁忙、限流、认证/额度错误、连接错误或超时后，对相同地址、凭据和模型组合默认冷却30秒。期间不同问题也不重复访问该故障配置；已有成功缓存仍可使用。
- 冷却结束后，由下一次用户请求重新尝试。更换模型地址、凭据或模型不会继承原配置的冷却状态。
- 冷却状态最多128项，存储在后端进程内。它不跨进程或重启共享，也不会撤销已发出的并发请求。
- AI_ROUTING_TIMEOUT_SECONDS和AI_FAILURE_COOLDOWN_SECONDS可通过环境变量调整。原18秒模型等待预算仍然保留；它不是完整HTTP请求的严格端到端耗时保证。
- 此机制减少故障期间的重复等待，不代表上游DeepSeek服务已经恢复，也没有新增可用的备用服务密钥。

## 评估与复查

数据集：back/evaluation/chat_intents.json，共42条人工编写的固定回归用例，覆盖食材、菜谱、库存、普通问答、追问、条件编辑、澄清。

执行方式（在back目录）：

```powershell
.venv/Scripts/python.exe scripts/evaluate_chat_intents.py --output ../output/algorithm-optimization/intent-evaluation.json
```

脚本只读本地目录和数据库，禁用模型调用，输出逐条预期、实际意图、是否澄清及混淆矩阵。

本次结果：42/42条符合预期；该固定集上意图与澄清判断一致率100%，普通问答误转推荐0条。这个数值只代表已公开的回归集，不等于真实用户总体准确率，也不能用于宣称相对旧版本提升百分比。

自动检查另外覆盖：明确推荐只调用一次模型、模糊请求不调用模型、故障冷却期间跳过请求、冷却结束恢复尝试、不同凭据互不影响、知识提问不修改条件，以及原有忌口和时间过滤。模型网络行为使用隔离模拟验证，没有将模拟耗时作为真实模型延迟。

报告可表述为：系统采用明确需求优先路由与模糊需求澄清机制，支持推荐对象切换和会话条件继承，并通过模型故障冷却减少无效重复调用。在42条固定回归用例中，意图及澄清判断均符合预期；真实用户采纳率、独立语料准确率和上游模型延迟仍需进一步采集。
