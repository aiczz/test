# AI核心算法优化记录

## 2026年10月16日：菜谱与食材之间的上下文衔接

- 后续补充活动话题与配料来源菜谱，支持“配料清单→展示这些食材以便添加→这些食材能做什么菜”的连续操作。匹配已有食材档案后生成可加入库存的卡片，按食材标识去重，不进行新的时令推荐，也不自动写入库存；未匹配项单独说明，不创建虚构食材。兼容已有仅保存配料话题的旧会话。
- 配料清单中的零、负数、非有限数或空用量按未注明处理，不展示为0克；无用量的蔬菜类、蛋白质类等分类标题不当作具体食材。未注明用量合并列出，保留真实正数用量。

- 在普通推荐路由之前解析事实追问。“需要什么食材”“这几道菜的配料”读取最近菜谱的实际配料与原始用量，不重新推荐时令食材，不依赖模型生成配料。
- 保存最近推荐对象类型、当前查看的菜谱/食材及配料或步骤话题；支持“第二道的配料”后接“怎么做”，也支持配料查询后用“第二道呢”切换目标。序号沿用推荐卡片顺序，不修改推荐数量。
- “这些食材能做什么菜”“能做什么菜”等使用最近食材检索关联菜谱，继续保留已声明忌口等条件。明确点名的新食材优先于旧食材引用。
- 前端发送最近可见推荐的类型，兼容旧会话已有的菜谱和食材标识。配料追问不覆盖原菜谱引用；库存仍以登记记录为准，列出配料不等于用户已拥有，未按人数自行换算用量。
- 缺少引用、序号越界、多个对象下的单数指代或多菜做法问题会询问具体目标；缺失配料、用量或步骤如实提示。以上为有界会话引用解析，不是任意自然语言指代都能准确识别的永久记忆。

## 2026年10月16日：整餐分类与复核

- 优先读取配料，区分植物性菜、混合菜、蔬菜内容和蛋白来源。番茄炒蛋可同时计入蔬菜与蛋白类；鱼香、蚝油和鸡精不用于推断主要蛋白来源。植物性筛选仍考虑蚝油等动物性调味料，数据不完整时不能视为饮食认证。
- 对规则组合和AI结果共同进行整餐复核：减少多道汤、缺少蔬菜或蛋白类及非汤菜蛋白来源重复。考虑已选菜单，采用严格改善的单菜替换，保留其余菜品顺序，只从同一合格候选池选择，不放宽原过滤条件。
- 明确的全素、只推荐汤要求优先于默认搭配，并在会话软偏好中保留。候选不足时不生成或引入候选池以外的菜。
- 修改模型菜单后，丢弃针对旧组合的总说明及理由，按最终实际菜单生成说明和摘要，轨迹记录替换情况。
- 对上一轮30组真实AI结果做离线回放，数据库与逐组候选哈希一致，没有新增模型调用。按同一套新分类，复核前和复核后的30组菜单均含蔬菜和蛋白类；此前14/30的标签指标存在混合菜漏计，不能把分类修正当作推荐效果提升。
- 回放中调整12组菜单，共15次单菜替换，多道汤菜单从3组降为0组。证据位于outputs/meal-review-final-20261016；这是保存结果的离线复核，不是新一轮模型生成或真人偏好测试。

## 2026年10月16日：扩大模型选菜空间

- 聊天推荐和配菜接口共同保留最多24道已通过现有硬条件过滤的候选，模型从中选择所需数量。规则整餐组合独立保留，作为模型不可用或选择无效时的完整回退方案。
- 提示词区分忌口、分类排除等硬条件和少洗锅、省事、少油、清淡、高蛋白等软偏好。软偏好在会话中继承并支持明确取消；配菜接口的自由文本时间、人数及忌口也先解析再执行过滤。
- 候选信息增加完整配料记录、主料、做法标签、时长来源、已选食材匹配及未确认已有主料。做法标签不是完整操作流程，配料和营养记录仍可能缺失；不承诺整餐用时、成品低钠或食材用量足够。
- 对模型选择检查候选范围、去重和数量。清洗后选择不足时，完整采用规则组合，丢弃不对应的模型说明；返回的整餐摘要按最终实际菜品重新计算。
- 以上属于推荐链路改进，不代表已经证明模型推荐质量提高。自动检查使用隔离模型响应，验证模型确实能选择规则参考组合之外的候选、无效响应回退、偏好继承和自由文本时间过滤；真实模型延迟和用户采纳率需要另行同环境对照。

本轮重点为需求识别、模型故障处理和可复现评估。

## 需求识别与连续对话

- 明确的食材、菜谱、库存和连续追问由本地规则先识别，避免每次都先请求模型分类。
- 明确的新推荐对象优先于上一轮话题。例如菜谱之后说“换一批食材”，切换到食材；食材之后说“再来三道菜”，切换到菜谱。
- 修改人数、时间、少盐要求时保留当前推荐类型。
- 推荐数量作为独立会话条件，默认3项，支持1至10道菜或种食材。识别“5道”“五道”“5到菜谱”等表达，区分人数和时间；“换一批”保留数量，“改成两道”更新数量。候选召回、整餐选择、模型提示和最终卡片使用同一数量，候选不足时明确告知，不放宽忌口等条件凑数。
- 会话保存最近推荐食材和菜谱的标识，以及最近8条用户/助手消息（每条最多1000字符）。前端已有的可见推荐也可作为引用输入，支持“用这些食材推荐菜谱”“用上面的”；食材引用不要求先写入库存。普通问答带上有限历史和推荐对象，开始新会话、账号切换继续使用原有隔离机制。记录随当前浏览器会话状态在本机保存，不是跨设备的永久记忆。
- “推荐一下”“安排一下”等未说明对象的请求先询问食材还是菜谱，返回needs_clarification，不生成卡片，也不调用模型。
- 知识问题和普通话题走直接问答；询问“低钠是什么意思”不会自动开启低钠条件。用户明确取消忌口的操作仍然有效。
- 只有规则无法明确处理的话题才尝试模型分类，分类等待配置默认为3秒。模型分类不是独立评测过的语义理解系统，长句、否定和多意图表达仍需继续扩充评估集。

## 模型调用与故障冷却

- 明确推荐请求省去分类调用，正常路径只调用一次模型完成选择和说明；未配置模型时继续使用算法结果。
- 已有成功响应缓存继续使用，容量128项、默认300秒。
- 模型繁忙、限流、认证/额度错误、连接错误或超时后，对相同地址、凭据和模型组合默认冷却30秒。期间不同问题也不重复访问该故障配置；已有成功缓存仍可使用。
- 冷却结束后，由下一次用户请求重新尝试。更换模型地址、凭据或模型不会继承原配置的冷却状态。
- 冷却状态最多128项，存储在后端进程内。它不跨进程或重启共享，也不会撤销已发出的并发请求。
- AI_ROUTING_TIMEOUT_SECONDS和AI_FAILURE_COOLDOWN_SECONDS可通过环境变量调整。原18秒模型等待预算仍然保留；它不是完整HTTP请求的严格端到端耗时保证。
- 此机制减少故障期间的重复等待，不代表上游DeepSeek服务已经恢复，也没有新增可用的备用服务密钥。

## 评估与复查

数据集：back/evaluation/chat_intents.json，共42条人工编写的固定回归用例，覆盖食材、菜谱、库存、普通问答、追问、条件编辑、澄清。

执行方式（在back目录）：

```powershell
.venv/Scripts/python.exe scripts/evaluate_chat_intents.py --output ../output/algorithm-optimization/intent-evaluation.json
```

脚本只读本地目录和数据库，禁用模型调用，输出逐条预期、实际意图、是否澄清及混淆矩阵。

本次结果：42/42条符合预期；该固定集上意图与澄清判断一致率100%，普通问答误转推荐0条。这个数值只代表已公开的回归集，不等于真实用户总体准确率，也不能用于宣称相对旧版本提升百分比。

自动检查另外覆盖：明确推荐只调用一次模型、模糊请求不调用模型、故障冷却期间跳过请求、冷却结束恢复尝试、不同凭据互不影响、知识提问不修改条件，以及原有忌口和时间过滤。模型网络行为使用隔离模拟验证，没有将模拟耗时作为真实模型延迟。

报告可表述为：系统采用明确需求优先路由与模糊需求澄清机制，支持推荐对象切换和会话条件继承，并通过模型故障冷却减少无效重复调用。在42条固定回归用例中，意图及澄清判断均符合预期；真实用户采纳率、独立语料准确率和上游模型延迟仍需进一步采集。
