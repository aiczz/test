# 食时 · 推荐算法与 AI 设计

> 面向「AI 算法 + 开源赛道」的技术说明：算法负责什么、AI 负责什么、边界在哪、
> 哪些地方是刻意的取舍。

---

## 一、一句话概括

**算法负责「选什么」，大模型负责「怎么说」。**

清洗库有 590 个核心食材、10000 道菜。把库直接交给大模型让它「推荐几道」，
它一定会编出不存在的菜名，或者推一道要炖三小时、而家里只有 45 分钟的菜。
所以分工被写死成：

```
综合打分算法（确定性）          大模型（可失败、可降级）
  ├ 从我们自己的库筛候选          ├ 只在候选集内挑选
  ├ 执行全部硬约束（忌口/限钠/时间）├ 写推荐理由
  └ 每日轮换（同地区同日一致）     └ 写当天的饮食建议
        ↓                              ↓
   用户硬约束再收口一次 ──────────→ 最终 3 + 3
```

## 二、首页推荐（`GET /api/home`）
### 2.1 数据来源

| 来源 | 用来干什么 | 规模 |
|---|---|---|
| `seasonal_food` + `seasonal_calendar` | **时令档位**（月份级 level='月份' / 季节级）+ 知识原文 | 544 + 52 |
| `ingredients` | 每 100g 营养、功效标签、中医宜忌、适宜人群、使用热度 | 8087（590 个核心食材）|
| `dishes` | 整菜营养（已按配料克重算好）、标签、营养置信度 | 10000 |
| `dish_ingredients` | 配料、克重、主料/辅料角色 | 77886 |
| `seasonal_dish_links` | 时令日历 ↔ 菜品显式关联（信号稀，当加分项） | 101 |
| Open-Meteo（外部，免费无 key） | 该城市实时气温/降水 → 饮食意图 | — |

### 2.2 打分公式

```
质量分 quality = 3.0·时令契合 + 1.6·天气适配 + 1.2·营养 + 1.8·口味偏好 + 0.8·大众接受度
最终分 score   = quality + 0.9·每日轮换因子
```

| 因子 | 怎么算 |
|---|---|
| 时令契合 | `seasonal_food` 的应季程度（月份级=100 / 季节级=85）→ **主序（档位）** |
| 天气适配 | 天气意图 × 关键词：冷→温/暖/炖汤；热→清热/凉菜/低脂；雨→祛湿/汤；燥→润肺/生津 |
| 营养 | 蔬菜蛋白搭配、膳食纤维；**限钠时**压低高钠食材 |
| 口味偏好 | 命中家庭成员的口味偏好标签 |
| 大众接受度 | 食材被多少道菜用到（`usage_count` 对数归一）；菜名可读性 |
| 每日轮换 | `sha256(地区 + 日期 + 条目名)` → 0~1，**确定性** |

### 2.3 「同地区同一天一样、跨天不一样」怎么实现

1. 轮换因子是**确定性函数** —— 同地区 + 同日期永远同一个值，
   所以那天所有用户看到完全一致的顺序（也正因此，AI 调用可以按地区共享）
2. 日期一变，因子全变 → 排序换了
3. **轮换只在同一时令档位内发生**：95 分的莲藕永远不会被 90 分的南瓜挤下去

⚠️ 选法上还分了两种情况：

| 场景 | 选法 | 为什么 |
|---|---|---|
| 首页每日推荐 | 档位 → 质量前 14 名组成池子 → 池子内按当日因子轮换 | 要「每天不一样」 |
| 「用我的食材能做什么」/ 配菜 | **相关性优先，不轮换** | 用户明确说「我有莲藕」，要的是能用莲藕的菜，不是「今天轮到哪道」。轮换会把它挤出去（实测踩过）|

### 2.4 AI 在哪一步介入

```
算法筛出候选（食材 8 个、菜品 8 道）
        ↓
每天每地区【只问一次】大模型 → 在候选集内挑 3 个 + 写理由
        ↓
模型返回的 id 不在候选集里 → 直接丢弃（幻觉防线）
        ↓
用户硬约束再收口一次（忌口 / 限钠 / 可用时间）
```

**缓存键** = `{配方版本}:{地区}:{日期}:{季节}:{天气}:{模型}`
→ 一个地区一天只调一次模型；**改了算法或提示词就把配方版本 +1**，旧缓存自然失效。

⚠️ 候选筛选**不带用户忌口**（否则缓存无法按地区共享）。代价见「五、已知边界」。

### 2.5 硬约束怎么执行

| 约束 | 执行方式 | 存在哪 |
|---|---|---|
| 忌口 | **硬过滤**，且带同义词表：辛辣→辣/花椒/麻辣/干辣椒/泡椒/咖喱 | `user_preferences.avoid_foods` |
| 可用烹饪时间 | **只在时长有依据时硬筛**；时长是估的则只降权（见下）| `user_preferences.cook_minutes` |
| 限钠 | 软性降权（按每餐钠含量，超过目标 1.6 倍明显扣分）| `user_preferences.low_sodium` |
| 人数 | 影响推荐文案与份量说明 | `users.family_size` |
| 口味偏好 | 影响排序权重，不覆盖健康约束 | `user_preferences.diet_preferences` |

**这些约束是存在服务器上的，不是只活在前端内存里。**
`GET/PUT /api/profile` 一读一写，前端登录后启动时拉一次、保存时推一次，
另外本机也留一份缓存（没登录 / 断网时不至于一刷新就丢）。

⚠️ 这里修过一个很显眼的 bug：家庭档案原先**只在前端内存里**，
前端从来没调过 `/api/profile` —— 于是「我的」页把人数从 3 改成 5，
切到首页和 AI 页看到的还是 3，刷新一下连「我的」页自己也变回 3。
约束是求解器的输入，不能只活在一次会话里。

校验：`tests/test_business.py::test_family_constraints_persist_and_reload`
（写进去、换一次请求读回来）、验收脚本第 9 组（6 个字段逐个往返 + 部分更新不清空）。

**关于烹饪时长**（一处重要的自洽性修正）：清洗库的 `dishes` 表**没有时长列**。
实测 10000 道菜里：
- **4386 道（43.9%）** 能从做法文本里抽出真实时长（「小火炖 30 分钟」→ 30）
- **5614 道（56.1%）** 抽不到，后端兜底填 30 —— 那是**编的**

于是有两条规则：

1. **筛选**：有依据 → 硬筛；没依据 → 降权，不否决。
   拿一个编出来的数字去删除候选，那不叫确定性约束，那叫瞎猜。
2. **展示**：有依据 → 「约 N 分钟」；没依据 → **「时长不详」，不显示数字**。
   以前两种情况都显示「约 30 分钟」，所以外观上 60% 的菜都「需要 30 分钟」
   —— 用户看到的是一屏假数字。宁可少一个信息，也不编。

`/api/recipes` 的响应里带 `duration_estimated` 标记，验收脚本第 10 组会检查
「两种来源都真的出现过」以及「估算值确实全部堆在 30」。

## 三、AI 助手页

### 3.1 界面结构

| 区域 | 内容 |
|---|---|
| 顶部渐变头 | 「小食 AI 助手」+ **「用我的食材配这一餐」**入口 + 快捷提问词 |
| 对话流 | 用户气泡 / AI 气泡 / **推荐流程轨迹卡** |
| 输入栏 | 单行输入 + 发送 |

**推荐流程轨迹（答辩的主要看点）**：
每一步都是后端**真实发生**的事，不是前端演的 ——
识别出的约束、召回了多少候选、哪些菜被硬约束否决、模型花了多少毫秒。
界面上会标注这份轨迹是「后端真实轨迹」还是「本地演示轨迹」（后端离线时）。

> ⚠️ **这里刻意不叫「多智能体协作」，因为它不是。**
> 它是一条**流水线**：读取约束 → 候选召回 → 硬约束否决 → 文案生成 → 模型定稿。
> 五个阶段里有四个是确定性代码，只有「模型定稿」一步真的调大模型。
> 把它说成「七个 Agent 协作」是往脸上贴金 —— 那种说法在答辩时经不起追问
> （「Critic Agent 在哪？它的否决权怎么实现的？」）。
> 界面上、代码里、文档里现在统一叫「推荐流程」。
>
> 真有七个 Agent 的那套实现存在于另一条未合并的分支上，**不在本次交付里**。

### 3.2 两条链路

**① 对话 `POST /api/ai/chat`**

第一步是**路由**：判断这句话是「闲聊」还是「用户表达了需求」。

⚠️ 这一点最初是错的：原来只有「命中固定短语才算推荐，否则算闲聊」，
实测 19 条常见说法里 **11 条判错**，而且最糟的是
「我想减肥」「最近想补气血」—— 食养诉求**已经解析出来了，却因为判成闲聊被整段丢掉**；
「我不吃香菜」这种忌口声明也被忽略（安全问题）。

现在改成**先抽信号、再决策**：

| 优先级 | 信号 | 判定 |
|---|---|---|
| ① | 追问（换一批 / 还有别的吗）| 继承上一轮意图 |
| ② | 提到自己的食材（我的/我家/家里 + 食材/库存…）| 走库存链路 |
| ③ | 餐次 / 吃喝 / 推荐词（吃什么·吃啥·来点·汤·菜·饭·推荐…）| 走推荐 |
| ④ | **食养诉求**（补气血 / 减肥 / 上火 / 失眠…）| 走推荐 + 诉求加权 |
| ⑤ | **点名了具体食材**（莲藕怎么做 / 西红柿炒蛋怎么做）| 走推荐 + **按该食材召回** |
| ⑥ | **声明了忌口**（我不吃鸡蛋 / 海鲜过敏）| 走推荐 + **加进硬约束** |
| — | 以上都没有 | 闲聊 |

原则：**宁可多推一次，也不能把用户明说的需求当闲聊敷衍过去。**

抽到的信号都会真实生效，并且写进轨迹（「识别到：食养诉求「补气血」；点名的食材 莲藕；声明的忌口 鸡蛋」）：

* **诉求** → 匹配我们自己的 `effects_json` 扩召回 + 打分加权（权重 2.4，高于天气）
* **点名食材** → 用它召回（「莲藕怎么做」→ 推荐的每一道都是莲藕菜）。
  别名也认：用户说「西红柿」，库里核心名叫「番茄」——
  590 个核心食材里 580 个（98%）带别名，只按名字匹配会认不出来
* **忌口** → 立即并入硬约束，并且从「口味偏好」里摘掉同名项

之后才进入推荐流程：

```
规则识别意图 → 按意图召回候选（时令 / 我的食材 / 点名食材）
    ↓
硬约束过滤 —— 被否决的写进轨迹（"确定性否决 47 道：土豆红萝卜炖牛肉（含「辣」）…"）
    ↓
模型在候选内挑 3 道 + 写一段回答
    ↓
校验 id → 失败则退回原有的纯规则实现
```

⚠️ **一条安全红线**：「条件太紧就放宽重试」这条兜底路径，
**只允许放宽「可用烹饪时间」，绝不能放宽忌口/限钠**。
原来的写法是重新构造一个中性约束，等于把用户的忌口丢掉 ——
后果是「我不吃鸡蛋」第一轮正确筛掉番茄炒蛋，兜底轮又把它推了回来。
现在单独抽成 `_relax_time_only()` 并配了测试。

**② 配菜 `POST /api/ai/recommend`**

```
用户勾选的食材 + 今日菜单已有的菜（必须排除）+ 家庭硬约束
    ↓
按食材召回：同时匹配核心食材 —— 点「鸡肉」也能召回用「鸡胸肉」的菜
    ↓
综合打分（时令/天气/营养/偏好/轮换）
    ↓
模型在候选内挑 N 道 + 写理由 + 说明和已有食材/已有菜单怎么搭配
    ↓
一键加入「今日菜单」
```

### 3.3 闲聊也要答到点子上

闲聊分支不是「一律回一段自我介绍」—— 那对「谢谢」「再见」就是答非所问。
现在按子类型给不同回复（问候 / 道谢 / 道别 / 问身份 / 问用法），
接了大模型时也明确要求它「先判断用户到底在说什么，不要把每种话都答成同一段介绍」。


### 3.3 设计上的几个取舍

| 取舍 | 理由 |
|---|---|
| AI 不做硬约束判定 | 过敏/限钠出错是危险的，必须由确定性代码兜住 |
| AI 挂了接口不报错、退回规则 | 演示现场断网也要能用；响应结构完全不变 |
| 配菜不轮换、结果可复现 | 用户重开面板应该看到同样的建议，而不是随机换一批 |
| 协作轨迹同时保留「真」与「演」两版 | 后端离线时界面不能空着；但必须标注清楚哪版是哪版 |
| 每个推荐都带理由与命中因素 | 让用户知道「为什么是它」，而不是一个黑盒列表 |

## 四、知识库（原创性与开源性的落点）

AI 的每一句话都建立在这些**我们自己清洗过**的数据上，不是模型的通用常识：

| 表 | 提供给 AI 的内容 |
|---|---|
| `ingredients` | 每 100g 营养、功效标签、中医宜忌、适宜人群 |
| `dishes` | 整菜营养（按配料克重算好）、标签、营养置信度 |
| `seasonal_calendar` | **时令知识原文**：「秋季（9月-11月）的应季蔬菜共 24 种：白萝卜、大白菜、山药、莲藕…」「秋季润肺，这样吃抗病魔！」 |
| `seasonal_food` | 逐条时令食材与推荐理由 |

提示词里会把这些**原文**贴给模型并要求引用。
所以界面上那句「10月应季蔬菜含山药、莲藕，秋季润肺这样吃抗病魔」是**我们的数据**说出来的。

### 食材标签的三级推导（保证每个食材都有标签）

清洗库的 `effects_json` 只覆盖 **124/590（21%）**。所以标签按优先级推导：

| 优先级 | 来源 | 覆盖 | 准确性 |
|---|---|---|---|
| 1 | `effects_json` 功效标签 | 124（21%）| 受源数据质量限制（见第五节）|
| 2 | **营养数值判定**：富含维生素C ⇐ 维C≥30mg/100g；低热量 ⇔ ≤40kcal… | 357（61%）| **准确**：9 条规则 0 反例，数值可核对 |
| 3 | `subcategory` / `category` 兜底 | 109（18%）| 真实但信息量最少（浆果/坚果种子/鱼/菌菇…）|

阈值集中在 `app/data/food_tags.py`，参照《中国食物成分表》常见分档。

### 菜品标签的归一化（保证每个分类点进去都有菜）

食材那边是「每个食材都有标签」，菜品这边的问题反过来：标签太多、太散、**和界面对不上**。

实测 `dishes.tags_json`：**985 个去重标签里有 571 个只出现一次**，同一件事有四五种写法：

| 同一件事的写法 | 归一后 |
|---|---|
| 汤羹(867) / 汤(226) / 煲汤(9) / 老火汤(3) | **汤羹** |
| 素菜(1394) / 素食(261) / 纯素(1) / 吃素(1) | **素菜** |
| 宴客(346) / 宴客菜(231) | **宴客菜** |
| 下饭菜(3130) / 下饭(93) | **下饭菜** |
| 面(90) / 面条(61) / 拌面(24) / 汤面(21) / 炒面(16) | **面点主食** |
| 家常(9xxx) / 私房菜 | **家常菜** |

前端原来写死 `['快手菜','汤品','低脂','家常','秋季推荐']`，而库里叫「家常菜」「汤羹」「低脂减重」——
**字符串对不上，所以除了「全部」每个分类点进去都是空的**。

现在的做法（`app/data/dish_tags.py`）：

1. **归一**：`_RULES` 是一张「关键词 → 规范名」的有序表，**从上往下第一条命中即返回**。
   985 个零散标签 → **45 个规范分类**，卡片上和筛选用的是同一套名字。
2. **分组**：45 个分类按语义分成 8 组（家常快手 / 品类 / 做法 / 主要食材 / 口味 / 人群·目标 / 菜系 / 其他），
   筛选区读起来像个目录，而不是 45 个平铺的 chip。
3. **不打乱顺序就不出错**：规则顺序本身就是逻辑，踩过三次坑，都有回归测试：
   - 「下饭菜」含「饭」→ 曾被宽泛的「饭」规则吃掉 3155 道菜，分类页显示 **0**；
   - 「年夜饭」同理；
   - 「鸡蛋」含「鸡」→ 曾被「鸡肉」规则吃掉 22 个标签。
4. **不丢长尾**：归不了的标签（「秋日暖汤」这种）**原样保留**在卡片上，只是不进筛选分类 ——
   否则筛选区会有 985 个 chip，等于没有筛选。
5. **名称兜底**：43 道菜 `tags_json` 是空的（「牛肉面」「煎牛排」「腊八粥」…），
   一个分类都归不出来时用**同一套规则扫一遍菜名**。

**覆盖结果**：10000 道菜里 **9996 道（99.96%）**至少落进一个分类。
剩下 4 道（青梅酒 / 肉豆蔻梨牛奶热饮 / 水果拼盘 / 蜜枣）是真的落在「家常菜」分类体系之外，如实留着。

分类由后端 `GET /api/recipes/tags` 提供，**带每个分类的菜品数**（只返回有菜的分类），
筛选走 `GET /api/recipes?tag=汤羹`。测试里有一条硬断言：
**分类区报的数字必须等于按这个分类筛出来的条数**，且一道菜不会因为多个原始标签命中同一分类而被重复计数。

## 五、已知边界（诚实清单）

| # | 边界 | 影响 | 建议 |
|---|---|---|---|

`check_web_ui.py` 值得单独说一句：**不要用 headless 截图来验证这个项目**。
Flutter web 画在 canvas 上，headless 的 `Page.captureScreenshot` 抓到的是
一张**不会更新**的旧帧（实测连点 5 个 tab，5 张 PNG 的 SHA256 一模一样），
