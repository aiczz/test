## 一、我（项目负责人）要做的：就一条命令

```bash
cd <这个文件夹>          # 里面应该是 .git / back / front / sql / deploy …
git push origin main
```

**在 push 之前**可以先跑一次体检（30 秒，确认没有漏提交、没有把密钥带上去）：

```bash
python back/scripts/repo_health.py
```

它检查四件事：
1. 有没有未提交的改动（有的话 push 会漏东西）
2. `.env` / 数据库 / 明文 key 有没有混进仓库
3. 和远端的差距（**落后 0** 才能干净快进，否则 push 会被拒）
4. 仓库里有没有「没人用的大文件」

push 完之后：**等 GitHub Actions 跑完**（约 3~5 分钟）。
在仓库的 `Actions` 页看到 `Build Web (自托管静态站)` 打绿勾，
并且 `Releases` 页出现新的 `web-latest` 产物，再叫队友部署。

> 为什么必须等：服务器上不装 Flutter，前端产物是 CI 构建好发布到 Release 的。
> **前端有改动而 CI 还没跑完就部署，页面上看到的还是旧版本** ——
> 这是最容易踩、又最难查的一个坑。

**详细步骤、密钥怎么填、出问题怎么查，全在 [`deploy/README.md`](deploy/README.md)。**

在服务器上跑（不需要在服务器上装任何东西）：

```bash

```

想看细一点，把验收脚本跑一遍（**49 项断言**，逐条对应设计要求）：

```bash
cd /opt/test/back
python3 scripts/verify_ai_features.py --base http://127.0.0.1
```

它检查的是**需求本身**，不是「页面能打开」：同地区同一天两次请求一致、

任何一条不过都会明确打印是哪一条。

> 脚本用到演示账号 `demo`，第一次部署时后端会自动种进去。

## 五、部署时最容易踩的三个坑（都已绕开，列出来是怕有人「优化」掉）

1. **前端产物里不能写死后端 IP。**
   现在是同源构建（产物里一个 IP 都没有），由 nginx 把 `/api/` 反代到后端。
   换 IP / 换域名 / 上 HTTPS 都不用重新构建。
   ⚠️ 别在 `build-web.yml` 里加回 `--dart-define=API_BASE`。

2. **compact 模式下新建的表不会被建出来。**
   新表必须同时加进 `back/app/core/database.py` 的 `STATE_TABLES`，
   否则 `create_all` 不会建它（AI 缓存表当初就是这么漏的）。

3. **给已存在的表加列，`create_all` 是不管的。**
   数据库已经建好之后再给模型加字段，新列永远不会出现，
   表现是「保存了偏好，一查就报 no such column」。
   现在是启动时按 `_ADDED_COLUMNS` 增量 `ALTER TABLE` 补上（幂等）。
   以后再加列，记得也写进那张表。

## 六、给答辩/演示用的一分钟讲法

- **数据是我们自己清洗的**：10000 道菜、590 个核心食材、596 条时令数据，
  不是模型编的常识；
- **推荐是可解释的**：时令 / 天气 / 营养 / 偏好 / 每日轮换五个因子加权，
  每一步都能在首页的「推荐依据」里展开；
- **AI 只做两件事**：在**已经按硬约束筛过的候选集内**挑选和写理由 ——
  忌口、限钠、烹饪时间由确定性代码先筛，安全性不依赖模型；
- **同地区同一天结果一致、跨天会换**：靠 `sha256(地区|日期|种类|名称)`
  做每日轮换因子，AI 结果按地区+日期落库，**一个地区一天只调一次模型**。
