## 二、审计发现的问题（已全部处理）

审计脚本 `audit.py` 逐项检查，发现 **4 类问题**，我把真实的和误报的分开说。

### ❗ 真问题 1：营养匹配错配（已修复）

这是**最严重的一个**，我自己引入的 bug。

《中国食物成分表》的命名规范是 `主体名（修饰语）［真别名］`：
- **圆括号里是修饰语**：`乌龟（肉）`、`带鱼（切段）`、`杏仁（原味）`
- **方括号里才是别名**：`芝麻油［香油］`、`番茄［西红柿］`

我一开始把**圆括号里的修饰语也当成了别名**，于是造出这些错误映射：

| 错配 | 正确应为 |
|---|---|
| `肉` → 乌龟 | 未命中 |
| `切段` → 带鱼 | 未命中 |
| `原味` → 杏仁 | 未命中 |
| `豆豉` → 鲮鱼（豆豉，熟） | 未命中 |
| `红色` → 青衣（红色） | 未命中 |
| `香蕉` → 香蕉（红皮）能量 81 | 香蕉［甘蕉］能量 86 |

**修复**：圆括号只用来截短主体名，只有方括号做别名；并加了优先级规则（`代表值` > `带方括号的正式条目` > `鲜` > 简短）。

修复后 `肉/切段/原味/豆豉/红色` 全部不再错配，`香蕉` 正确指向「香蕉［甘蕉］」。

### ⚠️ 误报 2：营养素数值"不一致"（审计脚本自己的问题）

审计报 `9/300 条数值不一致`，例如「腐竹 我们=485，来源=461」。

**查清后发现是我们没错**：成分表里有 **20 个重名条目**，`腐竹` 有两条（能量分别 461 和 485）。审计脚本用 `{名字: 行}` 字典比对时只取了第一条。

改成「该名字下所有取值」比对后：**300 条全部通过**。

### ⚠️ 误报 3：用料字符串"不一致"（格式归一化）

审计报 `1/2000 条不一致`。查清是 **id=1161「浓情巧克力蛋糕」**：语料里它的用料是**一个含换行的长字符串**，我们按分隔符聚合了。信息没丢，只是格式不同。

**经验**：菜谱用料应该用**换行**分隔，不是逗号。建议后续把 `dishes.ingredient_text` 的分隔符改成 `\n`。

### ❗ 真问题 4：27 道菜没有用料（源数据如此）

```
C1 用料为空的菜: 27    做法为空的菜: 0
```
27/200,000 = **0.0135%**，是源语料本身就空，不是解析丢的。建议入库时直接过滤。

### ❗ 真问题 5：中医关系几乎挂不到食材（已用图谱推导解决）

**这个差点做错。** 中医图谱里的关系边主要挂在**菜肴**上，不是食材：

| 边表 | START 端 | 条数 |
|---|---|---|
| 功效 | 菜肴 **860** / 食材 79 | 939 |
| 适宜人群 | 菜肴 **9673** / 食材 20 | 9,693 |

如果只按「食材→功效」直接取边，只能得到 **7 条**关联，等于没有。

**解决**：图谱里同时有 `主要食材`（菜肴→食材）87,968 条分解边，所以用**菜肴搭桥**推导：

```
食材 A -> 出现在菜肴 D 中 -> 菜肴 D 有功效 E -> 食材 A 具有功效 E
```

结果（这是图谱自身的推导，不是我们编的）：

```
食材-功效关联: 856 条（212 个食材）
食材-人群关联: 5,003 条（538 个食材）
```

抽查质量：

```
羊肉  -> 暖胃补肾, 益精气, 补肾阳, 暖腰膝, 温经止痛
山药  -> 补益气血, 健脾固肾, 补元气, 止咳润肺
红枣  -> 补脾益气, 养血补虚, 补元气, 润心肺
银耳  -> 滋阴润肺, 安神, 补气血
猪肝  -> 益目, 补肝, 养血, 明目
```

**但要如实说明**：只有 432 道菜有功效边，样本小，所以这些功效关联**是参考线索，不是医学结论**。

## 三之二、份量估重与菜品营养（新增）

### 背景：原来的营养全是 0

`dish_nutrition` 表一开始**完全没有用**，因为语料里大量用量是「2大片」「半盒」「3瓣」这种没有克数的单位，而原来只会解析 `\d+g/kg/斤/两`。

### 做法：三层回退估重

| 层级 | 规则 | 例子 | 占比 |
|---|---|---|---|
| 1. 显式克数 | 直接解析 | `100g` `1kg` `半斤` | 28.7% |
| 2. 食材单重 | 查 266 种食材的单件重量 | `2个鸡蛋` → 2×50g = 100g | 32.9% |
| 3. 同类均值 | 按分类兜底 | 未知叶菜 → 30g | 少量 |
| — | 模糊量按 0 计 | `适量` `少许` | 36.9% |
| — | 无法估算 | — | **1.5%** |

**有效覆盖率：有具体量的用料里 97.6% 能算出克数。**

### 结果

```
有热量值的菜: 135,216 / 188,049 (71.9%)
中位热量: 263 kcal      75%分位: 655 kcal      95%分位: 1830 kcal
称重可信度 >=90% 的菜: 81.0%
```

中位数 263 kcal 符合一顿家常菜的量级，说明估重基本合理。

### 脏数据保护

语料里有把说明文字当用量的情况，会算出 3.5kg、12000 kcal 这种不可能的值。加了两道闸：

- 单条用料上限 **1500g**
- 一道菜总重上限 **5000g**，超限的菜**不输出营养值**，只置 `suspect=1`

效果：最大热量从 3,950,592 kcal 降到 27,950 kcal。

### ⚠️ 使用注意

`dish_nutrition` 里所有数值都是**估算值**，依据是：
1. 《中国食物成分表》的**生食**每 100g 值
2. 常见食材的**标准单重**（如 1 个鸡蛋 50g）

**没有计算烹饪损失**（如维 C 加热分解），也没有考虑实际投料差异。
前端展示时应标注"营养为估算值，仅供参考"，不要作为医学或膳食建议。

### 4.1 14 张表都有对应数据文件

```
ingredient_categories.csv          13 行   15 大类（实际用到的 13 个）
ingredient_subcategories.csv       56 行   子类

ingredient_effects.csv            856 行   食材-功效
target_groups.csv                  76 行   人群字典
ingredient_groups.csv           5,003 行   食材-人群
dishes.csv                    200,000 行   ★ 菜品主表（含完整用料串+做法串）
dish_ingredients.csv        1,372,579 行   ★ 菜品-用料（含用量）
tags.csv                        5,610 行   标签字典
dish_tags.csv                 215,913 行   菜品-标签
dish_nutrition.csv            188,049 行   菜品营养汇总
schema.sql                                建表语句（14 张表）
```

### 4.2 外键完整性

```
C2 食材主表 id 连续无空洞 ......... 通过（建表时 AUTO_INCREMENT 生成）
C3 用料里的 ingredient_id 越界 .... 0 条
```

### 4.3 可以按这个顺序导入

```sql
-- 1) 建库建表
CREATE DATABASE recipe_db DEFAULT CHARSET utf8mb4;
SOURCE build/schema.sql;

-- 2) 按外键依赖顺序导入（父表先导）
ingredient_categories -> ingredient_subcategories -> ingredients
-> ingredient_aliases / tcm_effects / target_groups
-> ingredient_effects / ingredient_groups
-> seasonings -> dishes -> dish_ingredients
-> tags -> dish_tags -> dish_nutrition
```

**注意**：`dish_ingredients.ingredient_id` 和 `dish_tags.tag_id` 是按**文件行号**对应的，
所以 `main_ingredient.csv` 的**行序不能变**（第 1 行 = id 1）。
导入时用 `LOAD DATA INFILE` 或按行 insert，不要打乱顺序。

### 4.4 一个必须改的地方

`dishes.ingredient_text` 现在的分隔符是中文逗号 `，`。
**建议改成换行 `\n`** —— 因为源语料里有用料本身含逗号的（如 id=1161），
用逗号做分隔符会在前端展示时造成歧义。这个改动在 `build_dishes.py` 一行。
