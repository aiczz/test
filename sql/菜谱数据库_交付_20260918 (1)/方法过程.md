## 一、原始数据（三个文件夹）

| 文件夹 | 提供什么 | 规模 |
|---|---|---|
| `下厨房菜谱/` | 菜名、用料、做法、标签 | `recipe_corpus_full.json` 2 GB / 150 万道菜 |
| `营养物质组成表/` | **分类体系** + **营养素** | `food_composition_full.csv` 1,677 条 / 15 大类 61 子类 |
| `中医食补表/` | 功效、适宜人群、性味 | `D2hKG_Data-main/` 73,310 个节点 |

**关键发现一**：《中国食物成分表》的命名是 `主体名（修饰语）［真别名］`。
- 圆括号是修饰语：`乌龟（肉）`、`带鱼（切段）`
- 方括号才是别名：`芝麻油［香油］`、`番茄［西红柿］`

不解析方括号，覆盖率只有 22%；解析后升到 36%。**这是匹配环节的卡点。**

**关键发现二**：中医图谱的关系边主要挂**菜肴**而非食材（功效边：菜肴 860 / 食材 79），
必须用「菜肴搭桥」才能推到食材。

## 二、处理链路（六个阶段）

```
原始语料 2GB
   │
   ├─ ① process.py            解析用料字符串 + 导入 MySQL
   │      └ 产出：旧库六张表（1,550,151 道菜 / 622,689 个食材名）
   │
   ├─ ② clean_pipeline.py      食材名清洗
   │      ├ 规则清洗：剔除工具容器/说明文字/纯单位/配料标签；拆分拼接名；别名归一
   │      └ 中心词推断：统计名字末尾 2/3 字词频，高频尾词即真食材词
   │      └ 产出：622,689 → 15,459 个中心词
   │
   ├─ ③ build_main_ingredient.py   建食材主表
   │      ├ 解析成分表别名建索引 + 人工别名映射
   │      ├ 剔除调味料 3,569 个
   │      └ 产出：main_ingredient.csv 11,890 个食材
   │
   ├─ ④ estimate_weight.py        份量估重（三层回退）
   │
   ├─ ⑤ build_dishes.py           建菜品表
   │      └ 产出：dishes / dish_ingredients / dish_tags / dish_nutrition
   │
   ├─ ⑥ build_dict_tables.py      导出分类/功效/人群/标签字典
   │
   └─ ⑦ rebuild_tcm_via_dish.py   菜肴搭桥推食材功效/人群
```

### ① 解析用料（`process.py`）

核心是 `parse_ingredient()`，用量词白名单（按最长优先）确定切分位置。

旧实现的问题：正则里单位组是**可选**的，所以 `1个鸡蛋` 只匹配到 `1`，剩下 `个鸡蛋` 全被当成名字。

修复后能处理：
```
2大片生菜 → (生菜, 2大片)          1个鸡蛋 → (鸡蛋, 1个)
5ml料酒 → (料酒, 5ml)             适量盐 → (盐, 适量)
半根黄瓜 → (黄瓜, 半根)            1个七成熟水煮蛋 → (鸡蛋, 1个)
超市罐头装半盒金枪鱼(in spring water) → (金枪鱼, 半盒)
葱姜辣椒八角生抽耗油盐 → 葱|姜|辣椒|八角|生抽|耗油|盐
```

**39 项手工用例 + 2 万条真实语料抽样，可疑率 0.247%。**

### ② 食材名清洗（`clean_pipeline.py`）

622,689 条原始名 → 15,459 个中心词。

**为什么能塌缩这么多**：清理后发现 **99% 的名字只出现 1 次**，
而且大量是作者随手写的说明（`汤勺热油`、`咖啡杯大米`、`肉碎煮多少放多少`）。

**方法**：中心词几乎总在名字末尾（`黑山五花肉`→五花肉），
所以统计所有名字的末尾 2/3 字词频——**词表由数据涌现，不靠手写**。

加了两个保护：
- **前缀守卫**：`无糖抹茶粉` 不拆成 `糖`+`抹茶粉`
- **覆盖率检查**：`鸡蛋面` 不拆成 `鸡蛋`+`面`

### ③ 建食材主表（`build_main_ingredient.py`）

匹配策略按优先级：
1. **人工别名映射**（150 条，全部按成分表实际名称核对过）
2. 精确匹配
3. 去括号匹配

**刻意不做模糊包含匹配**——上一版这么做，把 `或者`、`添加`、`色素` 都配上了营养素，会静默污染数据。**食材匹配宁可漏不可错。**

同一食材在成分表里有几十个变体（鲜/干/罐头/品牌），用 `_entry_priority()` 选最基础的：
`代表值` > `带方括号的正式条目` > `鲜` > 简短 > 去品牌。

### ④⑤ 建菜品表 + 估重

**三层回退估重**：

| 层级 | 例子 | 占比 |
|---|---|---|
| 显式克数 | `100g` → 100g | 28.7% |
| 食材单重 | `2个鸡蛋` → 100g（50g/个） | 32.9% |
| 同类均值 | 未知叶菜 → 30g | 少量 |
| 模糊量按 0 计 | `适量`/`少许` | 36.9% |
| 无法估算 | — | **1.5%** |

**有效覆盖率：有具体量的用料里 97.6%。** 估重表覆盖 266 种常见食材。

### ⑥⑦ 中医属性

用菜肴搭桥：`食材 → 出现在菜肴中 → 菜肴有功效 → 食材有功效`
产出 856 条食材-功效、5,003 条食材-人群。

### 修复过的真问题 ❗

| # | 问题 | 后果 | 处理 |
|---|---|---|---|
| 1 | 把成分表圆括号里的**修饰语**当成别名 | `肉→乌龟`、`切段→带鱼`、`香蕉→红皮`（能量错 5 千卡），**静默污染** | 圆括号只截短名字，只有方括号做别名 |
| 2 | 中医关系只取食材边 | 只能得 **7 条**关联，等于没有 | 改用菜肴搭桥 |
| 3 | 营养字段名用英文键查中文列 | **热量/碳水/钙铁钠全是 0**，表建出来是空的 | 统一为中文列名 |
| 4 | 累计与写出的键名不一致 | `energy_kcal` vs `energyKCal`，**继续是 0** | 统一键名 |
| 5 | 脏用量算出百万级热量 | 最大 **3,950,592 kcal** | 单条上限 1500g + 单菜上限 5000g，超限不输出 |

### 两个「审计误报」（查明是我们没错）

- **"9/300 营养素不一致"**：成分表有 **20 个重名条目**（腐竹有两条，461 和 485），审计脚本只比了第一条。改成比对全部取值后 **300 条全通过**。
- **"1/2000 用料串不一致"**：id=1161 那条语料里的用料**本身含换行**，我们归一化了。信息没丢。

## 五、❗ 未解决的缺口：食材表 94% 没有分类和营养

**这是目前最大的问题，必须如实告诉你。**

### 现状

```
main_ingredient.csv 共 11,890 个食材

按引用次数分布：
   引用 1 次   : 8,098 个 (68.1%)   ← 长尾
   引用 >=2 次 : 3,792 个
   引用 >=10 次: 2,018 个           ← 实际常用的就这些
   引用 >=100 次:   894 个

有分类的食材: 544
有营养的食材: 544
```

### 问题所在

**引用 ≥10 次的 2,018 个常用食材里，只有 311 个有分类和营养。**

也就是说，**App 里最常被用到的食材，84% 查不到营养数据**。

### 为什么会这样

营养匹配依赖《中国食物成分表》，而它只收录 1,677 条。
清洗出的 15,459 个中心词里，只有 544 个能对上——因为：
1. 大量中心词本身就是脏数据（`个小葱`、`克味精`），不是真食材
2. 真食材的口语名和成分表标准名差距大（`蒜` vs `大蒜（白皮，鲜）`）
3. 成分表不收纯调味料

### 三个可选方案

| 方案 | 做法 | 结果 | 建议 |
|---|---|---|---|
| A. 加阈值过滤 | 食材表只留引用 ≥2 次的 | 3,792 个 | 简单，但仍有大量没营养 |
| B. **补人工映射** | 给引用 ≥10 次的 2,018 个逐个配成分表条目 | 2,018 个**全部有营养** | **推荐**，但要人工核对约 1,700 条 |
| C. 保持现状 + 标记 | 加 `has_nutrition` 字段，前端只对有营养的显示 | 11,890 个但只有 544 可用 | 最省事，但功能受限 |

**我倾向 B**：您项目的核心卖点是「营养/食补推荐」，如果常用食材都没营养数据，
这个功能就是空的。1,700 条人工核对大约是 1～2 天工作量。

## 六、旧库六张表要不要删 —— **建议删掉重建**

### 现状

```
recipes                        1,550,151 行
ingredients                      622,689 行   ← 未清洗
recipe_ingredient_names       10,637,147 行
recipe_ingredient_quantities  10,637,147 行
recipe_instructions            1,550,151 行
recipe_tags                    1,676,928 行
```

### 建议：删

**理由**：

| 旧表 | 新方案 | 差异 |
|---|---|---|
| `ingredients` 622,689 行 | `ingredients` 11,890 行 | 旧的是**未清洗**的原始名，含大量垃圾（`个茄子`、`汤勺热油`）。**用旧的会直接污染 App** |
| `recipe_instructions` | `dishes.instruction_text` | 合并进菜品主表了 |
| `recipe_tags` | `tags` + `dish_tags` | 新方案有标签字典，可以按类型筛选 |
| 营养 | 旧库完全没有 | 新增 |
| 分类 | 旧库没有 | 新增 |
| 中医属性 | 旧库没有 | 新增 |

**旧六张表除了「有 155 万道菜」之外，没有任何新方案没有的东西。**

### 两个选择

**选择一（推荐）**：删掉旧六张表，用新 schema 重建。

```sql
DROP TABLE IF EXISTS recipe_tags;
DROP TABLE IF EXISTS recipe_instructions;
DROP TABLE IF EXISTS recipe_ingredient_quantities;
DROP TABLE IF EXISTS recipe_ingredient_names;
DROP TABLE IF EXISTS ingredients;
DROP TABLE IF EXISTS recipes;
SOURCE build/schema.sql;
-- 然后按顺序导入 build/*.csv
```

**选择二**：保留旧的做备份，把新表建成 `v2_` 前缀，验证没问题再删。

### ⚠️ 但菜品数量的问题

旧库有 **155 万道菜**，新方案只导了 **20 万道**。
如果 App 需要更多菜品，跑：

```bash
python build_dishes.py 1550000     # 约 1 小时
```

## 七、最终的诚实结论

### 能直接用的
- ✅ 菜品：菜名、**完整用料字符串**、**完整做法字符串**、标签
- ✅ 菜品-用料关联（含用量 + 换算克数）
- ✅ 端到端逻辑链**已验证完整**（10/10 环节一致，营养口径手工复算一致）

### 需要标注才能用
- ⚠️ **菜品营养是估算值**。依据是《中国食物成分表》的**生食**每 100g 值 +
  常见食材标准单重。**没有计算烹饪损失**。前端必须写"营养为估算值，仅供参考"
- ⚠️ 中医功效/人群是**图谱推导的参考线索**，不是医学结论

### 不能用 / 需要先补
- ❌ **食材的分类和营养只覆盖 544 / 11,890**。常用食材里 84% 查不到营养
- ❌ `tcm_taste`（性味）字段**全是空的**——中医表里就没有这个数据
- ❌ `tcm_user` 只有 174 个食材有值

### 一句话

> **逻辑链是完整的、可追溯的，端到端追溯和手工复算都通过了。**
> 但**食材的营养覆盖是最大短板**——如果你要做营养推荐，
> 必须先补常用食材映射（见第五节方案 B），否则那个功能是空的。
