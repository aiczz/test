## 一、这份数据是什么

从**下厨房**语料（150 万道菜谱）出发，清洗出：

- **16,693 个食材名**（名字逐个核对过，已剔除调味料、碎片、截断名）

## 三、`main_ingredient.csv` 的 `quality` 字段

名字现在都是干净的，`quality` 只是**可用性提示**，不是"能不能用"的开关：

| 取值 | 含义 | 数量 | 用途 |
|---|---|---|---|
| `core` | 《中国食物成分表》里查到，有权威营养素 | ~650 | 需要热量/营养素时用它 |
| `common` | 语料里引用 ≥ 10 次 | ~1,800 | 常用食材 |
| `tail` | 其余（引用 3–19 次） | ~15,400 | 名字正确但少见，展示时按 `usage_count` 排序即可 |

```sql
-- 常见食材（按引用次数排序）
SELECT id, name, category_major, category_sub, usage_count
FROM ingredients
WHERE quality IN ('core','common') AND category_major <> '调味'
ORDER BY usage_count DESC;

-- 需要营养数据的场景
SELECT id, name, energy_kcal, protein, fat, cho
FROM ingredients WHERE quality = 'core';
```

## 四、导入 MySQL

**不要手写 INSERT。** CSV 的列名和表字段名不是一一对应的：

- 营养素列是中文（`能量kcal` / `蛋白质g`），表字段是英文（`energy_kcal` / `protein`）；
- CSV 只有「大类名/子类名」，表里要 `category_id` / `subcategory_id`；
- `instruction_text` 里有换行；
- 《成分表》里"没测"写作 `—`，直接塞 DECIMAL 会报 1366。

用随包的 `load_to_mysql.py`：

```bash
set MYSQL_HOST=localhost
set MYSQL_USER=root
set MYSQL_PASSWORD=你的密码
set MYSQL_DB=recipe_db

python load_to_mysql.py            # 建库 + 建表 + 全量导入 + 自动校验
python load_to_mysql.py --verify   # 只跑校验
```

⚠️ **不要单独重导一张表**（`--tables ingredients --truncate` 之类）。
`dish_ingredients.ingredient_id` 是外键且是 `ON DELETE SET NULL`，
单独清空 `ingredients` 会把所有菜品-食材关联清成 NULL。
要重来就整个库重建，脚本两分钟跑完。

**本机实测结果**（MySQL 8.0.46，全量导入约 2,000,000 行，约 2 分钟）：

```
食材总数 16693 / 有分类 16693 / core+common 2466
菜品总数 200000 / 菜-食材 1372579 / 菜-标签 215795 / 菜品营养 189587
外键脏数据: 0 / 0 / 0
番茄能做的菜: 8193
14 张表 CSV 与数据库行数逐表对账：全部一致
```

## 五、必须标注才能用的三条

1. **菜品营养是估算值**
   用《中国食物成分表》的生食营养值 × 估算克数加权算出，**没有计算烹饪损失**
   （维 C 加热分解、油炸吸油等都没算）。UI 文案必须是「估算值，仅供参考」。

2. **中医功效 / 适宜人群是参考线索，不是医学结论**
   图谱里功效边主要挂在菜肴上，食材功效是用「菜肴搭桥」推出来的，
   覆盖只有 1.4%。**不得呈现为医疗建议**，必须有免责说明。

3. **下厨房语料是 UGC，不得商用**
   只用于本次竞赛与作品演示，不对外分发原始语料。
   技术报告与《开源及第三方资源使用清单》里要写明来源与授权状态。

## 六、变更记录

### 第三轮：修掉"名字被截断"的**根因**（重要）

前两轮都在用手写映射补症状，这轮直接改了清洗算法的两处根因。

#### 根因 1：中心词词表只统计「末尾 2 字 / 3 字」

`clean_pipeline.build_tail_vocab` 原本只统计末尾 2-gram / 3-gram，还砍到 top 4000，
然后取"词表里能匹配到的最长词"。**任何超过 3 个字的食材名都会被砍掉前半截**，
因为 4 字以上的词根本不在词表里：

```
马苏里拉(4) -> 苏里拉     蔓越莓干(4) -> 越莓干
意大利面(4) -> 大利面     西兰花(3)   -> 兰花
黄瓜条(3)   -> 瓜条（"黄瓜条"频次不够，没进 top 4000）
```

**改法**：n-gram 统计到 8 字、不再砍 top_n；`head_word` 改为三条原则——
整名在词表里就用整名；**名字不超过 5 字一律原样保留**；
只有超长名才去截"最长的已知后缀"，截不出来也原样保留。

#### 根因 2：剥份量词时把食材名本身的前缀也剥了

`_strip_leading_quantity` 原本只要开头是数词/量词字就一路剥掉：

```
三文鱼 -> 文鱼      五花肉 -> 花肉     五香粉 -> 香粉
大白菜 -> 白菜      百香果 -> 香果     二锅头 -> 锅头
十三香 -> 香粉      七喜   -> 喜
```

**改法**：被剥掉的前缀里**必须含有真正的量词**（碗/勺/个/片/块/条…），
或至少两个程度字（大小点些许满整半）。单独一个数词不算份量。
`一小碗牛奶→牛奶`、`两片姜→姜` 仍然正确，但 `三文鱼` 不再被剥。

#### 顺带修掉的

| 问题 | 处理 |
|---|---|
| 别名在拆分路径上没生效，`西红柿` 和 `番茄` 变成两条食材 | 建表时补一遍别名归一（`西红柿→番茄`、`马铃薯→土豆`） |
| 同一个食材因切法不同被拆成多条（`葱/葱花/葱末/葱段`） | 新增形态合并：**去掉形态后缀后剩下的部分本身是食材**才合并（`粉条→粉` 不合并，因为"粉"不是食材） |
| 名字带装饰标点（`~鸡蛋`）在 MySQL 下和 `鸡蛋` 撞唯一索引 | 建表阶段做 NFKC + 去首尾标点 |
| 长尾里全是只用过 1 次的超具体名字（品牌名/整句话） | 食材表只收引用 ≥ 3 次的名字；用料原文一直保存在 `dish_ingredients.raw_name`，不会丢 |

**修复前后对照**（`audit_names.py` 的截断检测）：

```
                修复前      第二轮后     本轮（根因修复后）
疑似截断          491        431          394
  其中强证据      137          4            0
```

强证据 0 = 没有任何一个食材名是"另一个更长名字被砍掉前半截"的产物。
剩下的 394 个都是正常的包含关系（`葡萄酒` / `白葡萄酒`、`甘蓝` / `羽衣甘蓝`、
`荷叶` / `薄荷叶`），是各自独立的食材。

### 第二轮：手写映射补截断

| 问题 | 规模 | 处理 |

### 第一轮：结构与导入

| 问题 | 影响 | 处理 |
|---|---|---|
| 语料尾部残留非食材名（`己喜欢`/`可不放`/`等大小`/`皮材料`/`炸;`…） | 食材表脏 | 新增 `junk_rules.py` 统一规则 |

| 未解析「升」 | `1.5L` 判为无法估算 | 补 `L/升/公升` |
| `tcm_effects.name` 重名（`提神` x2 等 5 组） | 导入报 1062 | 按 name 去重 + 重映射 id（704 → 699） |
| 标签有 `KETO/Keto/keto`、`下午茶;/下午茶；` | 导入报 1062 | NFKC + 去首尾标点归一化合并 |
| 食材名带 keycap emoji（`⃣蜜豆`） | utf8mb4_general_ci 忽略组合符 → 撞唯一索引 → **静默丢数据** | 建表阶段就剔掉；导入改为遇错即报 |
| `INSERT IGNORE` 撞 UNIQUE 时静默跳行 | 数据少了却不报错 | 关键表改普通 INSERT；新增导入后逐表对账 |
| 旧文档数字过期 | 会误导开发 | 本文件为准；其余文档顶部已标注过期 |
