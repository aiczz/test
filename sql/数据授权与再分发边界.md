# 数据来源、授权状态与再分发边界

> 这份文件回答一个问题：**这个仓库里的数据，我们有权公开到哪一步？**
>
> 写它的原因：竞赛规则 §三(八) 明确写「公开可访问的资源不等同于当然具有复制、
> 训练、改编或再分发授权」，§四.8 要求「**不得上传无权公开或再分发的内容**」。
> 我们宁可把边界写清楚，也不愿意让评委替我们猜。

---

## 一、三个数据来源与各自授权状态

| 来源 | 提供什么 | 授权状态 | 业界通行做法 |
|---|---|---|---|
| **下厨房公开菜谱语料** | 菜名、用料字符串、做法字符串、标签 | 用户生成内容（UGC）。**仅限竞赛 / 研究用途，不得商用**；网站条款不允许批量抓取后再分发 | 不分发原始语料，也不分发等价于原始语料的成品表 |
| **《中国食物成分表》** | 食材分类体系（15 大类 / 61 子类）+ 每 100g 的 36 项营养素 | 正式出版物。营养数值本身是**事实性数据**，不受版权保护；但**整表汇编**与分类体系受保护 | 引用数值并注明出处，不复制原表结构 |
| **中医食补知识图谱（D2hKG）** | 功效、适用人群、性味、食用禁忌 | 依上游仓库 LICENSE（已在《开源及第三方资源使用清单》逐条列出） | 按上游许可使用并署名 |

## 二、当前仓库实际分发的内容（如实说明）

**原始语料从未进入本仓库** —— 原始的下厨房语料是约 2 GB 的
`recipe_corpus_full.json`，`.gitignore` 里 `data_delivery/` 与 `*.zip` 已挡住，
它也从未被提交过。

但**由该语料清洗加工出来的成品数据表，目前确实在仓库里**：

| 位置 | 大小 | 数量 |
|---|---|---|
| `sql/cleaned_v2/` | 约 45 MB | 39 个 `.csv` |
| `sql/catalog_v1/`（精选 700 道，线上实际使用的目录） | 约 4 MB | 6 个 `.csv` |
| `sql/knowledge_base/`（逐条菜谱/食材知识文本） | 约 18 MB | 2 个 `.txt` |
| `sql/菜谱数据库_交付_20260918 (1)/` | 约 18 MB | 10 个 `.csv` |
| `sql/seasonal_source/` | 约 0.1 MB | 3 个 `.csv` |
| `sql/cleaned_v2.zip` | 24.4 MB | 1 个压缩包（**内容与 `cleaned_v2/` 重复**） |
| **合计** | **约 101.4 MB / 59 个文件** | |

**为什么这是个问题**：`cleaned_v2/dishes.csv`、`db_dishes.csv` 这类文件里装的是
菜名、用料、做法 —— 也就是下厨房的 UGC 内容，只是被清洗过。
「清洗」不改变内容的权利归属。所以仓库里那句「不对外分发原始语料」在字面上成立，
但**在评审视角下站不住**。

而 `sql/` 下真正属于**团队自研**的东西只有 **0.4 MB / 21 个文件**：清洗脚本、
建表 SQL、字段说明、清洗报告、验证报告 —— 这些**完全有权公开**，而且足够撑起
「开放成果与复用价值」那一项。

## 三、处理方案

### 方案 A · 如实披露 + 划清边界（**必须做**，1 小时）

无论最终删不删文件，下面三件事都要做：

1. 在《开源及第三方资源使用清单》里如实填写三个数据来源、版本、获取方式、
   授权类型与关键义务；
2. 在技术报告里说明：数据仅用于本作品的功能实现与效果验证，**不对外分发原始语料**；
3. 仓库里保留本文件，把边界写在明处。

> 依据：规则 §四.8 允许「涉及第三方许可限制……的，应采用**适当的受限访问或
> 仅提供必要说明**」；评审说明第 5 条也给了「材料披露不完整」的一次限期补正机会。
> 但**披露与仓库实际做法必须一致** —— 这是方案 A 的前提。

### 方案 B · 撤下成品数据表（**推荐**，半天）

把上面第二节那 59 个文件从公开仓库撤下，**只保留 21 个自研脚本与文档**：

```bash
# 在仓库根目录执行。--cached 只从版本控制移除，本地文件会保留下来。
git rm -r --cached "sql/cleaned_v2" "sql/catalog_v1" "sql/knowledge_base" \
                   "sql/seasonal_source" "sql/菜谱数据库_交付_20260918 (1)" \
                   "sql/cleaned_v2.zip"

# 再把上面这些路径写进 .gitignore，避免以后又被 git add 进去
```

撤下之后：

- 仓库体积从 **367 MB 降到约 265 MB**，评委克隆快很多；
- `sql/` 只剩脚本 + 建表 SQL + 字段说明 + 清洗报告 + 验证报告，权利边界干净；
- 数据本体改为「按需申请」（规则明确允许受限访问）；
- 线上实例不受影响 —— 服务器上的数据库是独立的一份，不依赖仓库里的 CSV。

**代价**：别人不能 clone 下来一键复现完整数据。可以在 `sql/README.md` 里写清
获取方式，并把「如何从原始语料重新构建」的脚本保留好。

### 方案 C · 数据迁到私有仓库 / 网盘（最稳，1 天）

方案 B 再加一步：把撤下的 CSV 放到私有仓库或网盘，写清申请方式。
适合对再分发风险零容忍的情况。

## 四、关于 git 历史

⚠️ **方案 B / C 只影响「现在能看到什么」，不影响历史。** 撤下之后，
`git log -p` 仍然能翻到那些提交里的数据。

彻底清理需要重写历史：

```bash
# 需要额外安装 git-filter-repo；会改变所有 commit hash
git filter-repo --path sql/cleaned_v2 --path sql/catalog_v1 \
                --path sql/knowledge_base --path sql/seasonal_source \
                --path "sql/菜谱数据库_交付_20260918 (1)" --path sql/cleaned_v2.zip \
                --invert-paths
```

**代价**：所有 commit hash 改变，**需要队友配合 force-push**，
Release 里的构建产物与 commit 的对应关系会断掉。

**建议的取舍**：如果时间紧，**先做方案 A + B**，把「已披露 + 已停止分发」
这个事实固定下来；重写历史可以放在初赛提交之后再评估。
比赛规则对「材料披露不完整」给了补正机会，而对「知识产权侵权」是一票否决 ——
**披露清楚 + 停止分发** 才是把风险压到最低的组合。

## 五、明确不包含的内容

参赛材料中**不包含**，也**不得包含**：

- 任何账号密码、API 密钥、访问凭据（`.env.example` 里所有密钥字段均为空值）
- 任何个人信息
- 无权再分发的第三方原始资源
- 上游项目的模型权重或数据集
