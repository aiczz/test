## 1. 项目概述

### 1.1 一句话定位

**三餐智囊是一个家庭饮食决策多智能体系统**：输入家庭成员的库存、预算、口味、健康约束与本周时间安排，输出**可直接执行的"吃什么 + 买什么"方案**，并根据反馈持续学习。

### 1.2 为什么这是一道好题（而不是套壳 Chatbot）

"吃什么、买什么菜"看起来像闲聊，本质上是一个**带不确定性的约束优化 + 偏好学习 + 序贯规划**问题：

| 特征 | 说明 | 带来的算法价值 |
|---|---|---|
| 目标可量化 | 营养达标率、日均成本、食材浪费率、偏好满足度 | 可出**数字**，可做消融实验 |
| 约束是硬的 | 过敏、禁忌、钠上限、预算、厨具、时间 | 必须用求解器，LLM 靠不住 |
| 有真实权衡 | 省钱 vs 健康 vs 省事 | 天然适合多目标优化与 Pareto 前沿 |
| 有时序耦合 | 今天买的菜要在这周内用掉 | 保质期感知的批量规划，真问题 |
| 可离线仿真 | 合成家庭 + 模拟用户 | **可复现评测**，不依赖真人 |
| 多智能体天然分工 | 营养、库存、采购、口味各管一摊 | 多智能体不是装饰，每个 Agent 是约束拥有者 |
| **价格数据官方可得** | 农业农村部批发价 + 省市公共数据开放平台零售价 | 评测用**真实价格**而非自编价格，结论可溯源 |

**关键判断：本项目的竞争力不在"用了多智能体框架"，而在"用确定性求解器兜住硬约束 + 用可复现评测证明它比 baseline 更好"。** 这是绝大多数参赛队伍交不出来的东西。

### 1.3 目标定位（三者均衡的现实版本）

团队希望兼顾"算法创新 + 开源工程 + 产品落地"。在 30 天、新手为主的约束下，我们的策略是：

- **算法**：不做宽而浅，做**两个深点**（保质期感知的采购批量优化 + 偏好学习），并用**完整的消融实验**证明其增益
- **开源**：不靠人力堆，靠**模板化基础设施**（CI、Docker、文档、模板一次性搭好），成本低、评分高
- **产品**：不做双端原生，做**响应式 Web + PWA**，一份代码拿到"网页 + 手机 App"两种观感

### 1.4 交付形态【冻结】

- **主交付**：响应式 Web 应用 + PWA（可添加到手机主屏、全屏无浏览器栏、离线缓存）
- **备选**：如确需 `.apk`，最后用 Capacitor 包壳（约 1 天工作量）
- **放弃**：Flutter / React Native 原生双端开发

> 理由：移动端原生开发在"AI 算法精英大赛"评分中几乎不加分，却会消耗 7–10 天（打包、签名、双端调试）。PWA 在答辩现场的表现与 App 无差别。**把省下的时间投入评测与求解器，收益高一个数量级。**

### 1.5 差异化亮点

1. **LLM 管"软"，求解器管"硬"** —— 大模型只负责候选生成与解释，营养/过敏/预算/保质期全部由 CP-SAT 求解，杜绝幻觉导致的危险建议
2. **保质期感知的浪费最小化** —— 直击"买菜"环节的真实痛点，可量化（浪费率）
3. **Pareto 滑杆实时重解** —— 拖动"省钱↔健康↔省事"，毫秒级响应，演示冲击力最强
4. **可复现的家庭饮食评测基准** —— 合成家庭仿真器 + 消融表，可开源反哺社区
5. **接入官方公示的农产品价格数据** —— 农业农村部批发市场价格 + 省市公共数据开放平台的农贸市场零售价，价格真实可溯源，评测不再依赖"自编价格"（详见 5.1）
6. **中式饮食语境** —— 中式食材替换（没有生抽→老抽+糖）、时令、菜场分类，而非英文通用 Demo
7. **地域感知的菜系先验** —— 新用户不再冷启动：按所在地区调整菜系权重，第一周就能给出合理推荐（见 4.2）
8. **跨周记忆与学习** —— 结构化记录历史方案与反馈，按时间衰减调整推荐；评测用**学习曲线**证明它真的在变好（见 4.2 / 6.3）

## 2. 问题定义与数学形式化

### 2.1 输入

| 输入项 | 形式 | 来源 |
|---|---|---|
| 家庭成员 | 人数、年龄、慢病标签、过敏原 | 用户填写 |
| **地域** | 城市 / 地区 | **自动定位预填 + 手动覆盖**；驱动菜系先验（4.2）与价格管道（5.1），城市路由与降级见 4.6 |
| 预算 | 元 / 周（或元 / 天） | 用户设定 |
| 口味画像 | 辣度、油腻度、忌口食材、偏好菜系 | 地域先验 + 冷启动问答 + 在线学习（4.2） |
| **历史方案与反馈** | 结构化记忆事件流（采纳/拒绝/替换 + 原因 + 上下文） | 系统自身产生（4.2） |
| 库存 | 食材 → 数量 + 购入日期 | 手动输入（拍照识别列为 Later） |
| 厨具 | 可用厨具集合 | 用户勾选 |
| 时间 | 每日可用烹饪时长（可标"加班日"） | 用户设定 |
| 价格 | 食材 → 单价（批发价 + 零售价双源，经归一化与折算） | **官方公示数据**：农业农村部批发市场价格 + 省市公共数据开放平台农贸市场零售价；本地快照缓存 |

### 2.2 输出

1. **七日菜单**：每天每餐做哪几道菜、几份
2. **采购清单**：按菜场/超市货架分类的食材与数量、总价
3. **决策解释**：为什么推荐这道菜（哪个约束是紧的、消耗了哪些临期食材、**是地域习惯还是你的历史偏好**）
4. **权衡曲线**：一组非支配解，供用户拖动切换

### 2.3 形式化模型

**集合与参数**

```
D = {1..7}              天
M = {早, 午, 晚}         餐次
R                      候选菜谱集合（见 4.1 分层求解）
I                      食材集合
a[r][i]                做 1 份菜 r 需要食材 i 的量
n[r][k]                1 份菜 r 的营养素 k 含量（热量/蛋白/钠/蔬菜量）
t[r]                   菜 r 的烹饪时长（分钟）
e[r]                   菜 r 所需厨具集合
p[i]                   食材 i 单价
sl[i]                  食材 i 的保质期（天）
u[i]                   食材 i 的单位（克/毫升/个）
```

**决策变量**

```
x[r][d][m] ∈ {0,1}     第 d 天第 m 餐是否安排菜 r
s[r][d][m] ∈ Z+        份数
y[i]       ∈ Z+        食材 i 的采购量
Inv[i][d]  ≥ 0         食材 i 在第 d 天结束时的库存
W[i][d]    ≥ 0         食材 i 在第 d 天的浪费量
```

**目标函数（加权和，权重由前端滑杆给出）**

```
min   α · Cost  +  β · Waste  +  γ · (1 − Pref)  +  δ · NutriDev  +  ε · Monotony

其中
  Cost      = Σ_i p[i] · y[i]                                    采购总成本
  Waste     = Σ_i Σ_d W[i][d]                                    总浪费量
  Pref      = Σ ( x[r][d][m] · s[r][d][m] · pref(r) ) / 总份数     偏好满足度（0..1）
  NutriDev  = Σ_k max(0, 目标值_k − 实际值_k) / 目标值_k            营养偏差
  Monotony  = 7 天内重复主食材的惩罚项                             多样性惩罚
```

**硬约束**

```
(C1) 库存平衡
     Inv[i][d] = Inv[i][d-1] + y[i]·[d = 到货日] − Σ_{r,m} s[r][d][m]·a[r][i] − W[i][d]

(C2) 保质期（先入先出）
     若 d ≥ 到货日 + sl[i]，则 Inv[i][d] = 0（未用完即计入 Waste）

(C3) 过敏与禁忌（绝对约束）
     x[r][d][m] = 0,  ∀r 含任一家庭成员的过敏原或宗教/健康禁忌

(C4) 营养下界（按人天折算）
     Σ_{r,d,m} s[r][d][m]·n[r][热量] ≥ 热量下界 × 人数 × 天数
     Σ_{r,d,m} s[r][d][m]·n[r][蔬菜] ≥ 蔬菜下界 × 人数 × 天数
     Σ_{r,d,m} s[r][d][m]·n[r][蛋白] ≥ 蛋白下界 × 人数 × 天数

(C5) 钠上限（高血压成员采用更严阈值）
     Σ_{r,d,m} s[r][d][m]·n[r][钠] ≤ 钠上限 × 人数 × 天数

(C6) 预算
     Σ_i p[i]·y[i] ≤ B

(C7) 每日时间预算
     Σ_{r,m} x[r][d][m]·t[r] ≤ 当日可用时长（加班日取更小值）

(C8) 厨具可行性
     x[r][d][m] = 0,  ∀r 满足 e[r] ⊄ 现有厨具

(C9) 结构约束
     每餐主菜数量 1..2；每日至少 1 道蔬菜；不得连续 3 天重复同一道菜

(C10) 临期优先消耗（软化为目标惩罚项，避免不可行）
     W[i][d] 对临期食材加权，权重随剩余保质期递减
```

**求解器**：OR-Tools CP-SAT，单次求解时限 3–5 秒，返回**可行解**或**不可行证明**。

**解释性输出**（演示亮点）：当约束导致选择受限时，求解器可输出哪条约束是"紧的"（例如"本周成本已达预算上限的 98%，因此未推荐牛肉"），将其自然语言化后作为推荐理由。

## 3. 系统架构与多智能体设计

### 3.1 总体分层【冻结】

```
┌─────────────────────────────────────────────────────────────┐
│ L4 交互层   React + Vite + Tailwind (PWA)                    │
│            菜单板 / 采购清单 / Pareto 滑杆 / 协作轨迹可视化      │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST (OpenAPI)
┌───────────────────────────▼─────────────────────────────────┐
│ L3 决策层   CP-SAT 规划器（确定性，无 LLM）                    │
│            菜单选择 + 份量 + 采购批量 + 浪费最小化               │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│ L2 智能体层（固定流水线 + Critic 否决）                         │
│  Profile → Retrieval → Nutrition → Inventory → Procurement   │
│                            ↓                                  │
│                       ★ Critic（否决权）                       │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│ L1 记忆感知层  库存 / 反馈历史 / 口味画像 / 价格缓存              │
│                SQLite + JSON 数据表                            │
└─────────────────────────────────────────────────────────────┘
```

**核心设计原则：LLM 负责"软"的部分（理解需求、生成候选、自然语言解释），求解器负责"硬"的部分（营养、预算、保质期、时间、过敏）。二者之间通过结构化 JSON 契约交互。**

### 3.2 多智能体角色定义

| Agent | 职责 | 实现方式 | 输入 → 输出 |
|---|---|---|---|
| **Profile Agent** | 维护家庭画像、**地域先验**、**跨周记忆**、约束清单 | LLM + 规则 + 偏好模型（4.2） | 表单 / 历史反馈 → 结构化 Profile + 偏好分数 |
| **Retrieval Agent** | 从菜谱库召回候选（混合检索） | BM25 + 向量 + 食材替换图 | Profile → 候选菜谱集（60–100 道） |
| **Nutrition Agent** | 计算营养向量、校验膳食结构 | **纯确定性代码** | 菜谱集 → 营养参数 + 违规标记 |
| **Inventory Agent** | 库存与保质期管理、临期预警 | 确定性代码 | 库存 + 日期 → 临期清单 |
| **Procurement Agent** | 价格查询、采购量计算、分类清单 | 确定性代码 + Provider 接口 | 菜单 → 购物清单 + 成本 |
| **Planner Agent** | 调用 CP-SAT 求解、生成 Pareto 集 | **求解器封装** | 全部约束 → 菜单方案 |
| **Explainer Agent** | 生成推荐理由、约束松紧解释 | LLM（只读求解结果） | 求解结果 → 自然语言解释 |
| **★ Critic Agent** | 安全否决：过敏/禁忌/钠超标 | **确定性规则引擎（非 LLM）** | 方案 → 通过 / 否决 + 原因 |

### 3.3 Critic 否决机制（本项目的"多智能体"灵魂）

多数队伍的"多智能体"只是把一次 LLM 调用拆成四次。我们的设计让协作**有真实后果**：

```
Planner 产出方案
      ↓
Critic 确定性校验                    ← 不用 LLM，杜绝幻觉
      ↓
  ┌───┴────┐
通过       否决
  ↓          ↓
交付    生成新的硬约束，回灌 Planner 重解
             ↓
         最多迭代 3 次；仍不可行则输出"不可行报告"（告诉用户放宽哪条约束）
```

**为什么关键**：Critic 拥有**否决权**且**不可被 LLM 说服**，这让"多智能体协作"从修辞变成可验证的机制。评测中的"安全违规数"指标必须恒为 0。

### 3.4 为什么不用复杂的协商/辩论协议

考量为**新手团队 30 天可维护性**。自由辩论型协议（debate / auction）调试成本高、结果不可复现。**固定流水线 + 一票否决**同样体现多智能体分工，且每一步可单独测试、可单测、可解释。若时间富余，可在 W4 作为一个"对比实验"加入辩论型编排，反而成为论文式亮点。

## 4. 核心算法设计

### 4.1 分层求解策略（工程必需）【冻结】

直接对"7 天 × 全菜谱库"求解会爆炸。采用三级分解：

```
Stage 1  检索与候选生成
         混合检索把菜谱库（200–300 道）缩到 60–100 道
         依据：口味匹配、厨具可行、过敏过滤、时令、**地域菜系先验（见 4.2）**

Stage 2  周菜单求解（CP-SAT 主战场）
         7 天 × 3 餐 × 候选集
         输出：菜单 + 份数

Stage 3  采购批量优化（小规模 MILP / 贪心 + 局部搜索）
         给定菜单，最小化 成本 + 浪费，服从保质期与先入先出
         ← 这是"我们最深的一个算法点"
```

**Stage 3 的算法价值**：这是经典的 **shelf-life-aware lot-sizing** 问题。朴素解会买刚好够用的量，但受"包装规格 + 保质期"约束，实际会产生浪费。我们的模型允许**跨菜谱复用同一食材**（例如买一把葱分配给 4 道菜）并在临期时**优先消耗**，从而压低浪费率。这个指标可以在评测里直接对比出增益。

### 4.2 统一偏好状态模型（地域先验 + 个人记忆）⭐ v1.2 升级

**设计出发点**：地域偏好与历史记忆**不是两个独立功能，而是同一个偏好模型的两个信息来源** —— 地域是**先验**（冷启动用），个人反馈是**似然**（越用越准）。做成两个各自为政的模块会导致逻辑冲突、重复实现和维护成本翻倍。

**统一公式**

```
pref(u, r, ctx, t) =
      w_geo  · GeoPrior(r, region(u))                     ← 地域先验（冷启动）
    + w_pers · Σ_{f ∈ F(u)} e^(−λ(t − t_f)) · Like(f, r)   ← 个人长期记忆（时间衰减）
    + w_ctx  · Ctx(ctx, r)                                 ← 上下文（星期 / 天气 / 加班）
    − w_rep  · Rep(r, t)                                   ← 近期重复惩罚（短期记忆）
```

**四个分量的职责与实现**

| 分量 | 含义 | 实现 | 作用阶段 |
|---|---|---|---|
| **地域先验** `GeoPrior` | 该地区人群对菜系 / 菜品的先验偏好 | 菜系归属 + 地域→菜系偏好表（手工构建） | **解决冷启动**：新用户第一周就有合理推荐 |
| **个人长期记忆** | 用户历史接受 / 拒绝 / 替换 | Bradley-Terry + **指数时间衰减** `e^(−λΔt)` | 越用越准；旧反馈自然淡出 |
| **上下文** `Ctx` | 星期几、天气、是否加班 | 上下文老虎机（LinUCB），L3 有余力再做 | 捕捉"周一忙、周末做大菜"的周期规律 |
| **重复惩罚** `Rep` | 上周做过的菜，本周降权 | 近期频次衰减 | 避免"连着三周吃同一道菜" |

**时间衰减的意义**：3 个月前的一句"不想吃芹菜"不应永久生效 —— 那可能只是当时的心情。用 `λ` 控制记忆半衰期（建议 2–4 周）。**这本身就是一个可消融、可量化的点**（见消融 A8）。

**地域先验怎么建（诚实做法）**

不要把地域数据包装成"我们发现当地人最爱吃 X"的伪大数据。**诚实且够用**的做法是用菜系归属映射表：

```
地域 → 菜系偏好权重表（手工构建，约 100–200 行）
  四川 → 川菜 0.45 / 湘菜 0.15 / 家常 0.20 / 粤菜 0.08 / 其他 0.12
  广东 → 粤菜 0.40 / 家常 0.25 / 客家 0.10 / 川菜 0.10 / 其他 0.15
  东北 → 东北菜 0.40 / 鲁菜 0.20 / 家常 0.25 / 其他 0.15
```

来源：公开的地方饮食文化资料 + 菜谱库自身的菜系标注 + 常识。**几十行映射表就足以驱动冷启动** —— 不必、也不应去爬点评类平台。数据来源在文档与答辩中如实标注为"经验性先验"，这比夸大数据更经得起追问。

**地域不止影响菜系 —— 它是贯穿性维度**

| 联动点 | 说明 |
|---|---|
| **食材可得性** | 北方冬季叶菜少而贵 → 地域影响候选集 |
| **价格管道** | 官方价格数据本身就是分城市的（见 5.1）→ 地域直接复用 |
| **时令 / 节气** | 地域 + 时令共同决定"当季"判断（见 4.5） |

**记忆的数据结构（必须结构化，不能靠塞对话历史）**

```json
// data/memory/events.jsonl —— 每条是一次决策与反馈
{"ts": "2026-09-08T18:20:00", "user": "u01", "week": 36,
 "dish_id": 1042, "action": "adopted",
 "reason": "too_spicy",
 "context": {"dow": 1, "overtime": true, "weather": "rain"}}
```

`action ∈ {adopted, rejected, replaced, cooked, skipped}`；`reason` 为用户可选的原因标签。

**为什么必须结构化**：如果只是把历史对话塞进 prompt，那就是套壳 —— 无法评测、无法消融、无法解释。结构化事件流让 ① 偏好模型可直接更新，② 评测可统计，③ 前端能展示"为什么我记得你不吃辣"。

**落地分层（避免 scope 爆炸）**

| 层 | 内容 | 优先级 |
|---|---|---|
| L1 | 结构化记忆表 + 重复惩罚 + 地域先验 + 把历史反馈注入 LLM 上下文 | **必做** |
| L2 | 个人长期记忆的指数时间衰减 | **推荐做** |
| L3 | 上下文老虎机（星期 / 天气 / 加班作为 context） | 有余力再做 |

#### 4.2.1 基础在线更新机制（v1.0 原有，保留）

**冷启动**：8–10 道是非题（"能接受辣吗""吃内脏吗""讨厌香菜吗""愿意吃剩菜吗"）→ 初始化口味向量。

**在线更新**：
- 每次用户**接受 / 拒绝 / 替换**产生一个成对比较样本
- 用 **Bradley-Terry 模型**估计菜谱/食材的偏好分数（简单、稳定、样本需求小）
- 在候选集内用**上下文老虎机（LinUCB）**做少量探索，避免推荐塌缩到同几道菜

**进入优化**：偏好分数进入目标函数的 γ 项（v1.2 后使用统一偏好分数 `pref(u, r, ctx, t)`，本节机制是其"个人长期记忆"分量的基础）。求解器天然会在"用户爱吃"与"营养达标"之间找平衡，而不是让 LLM 拍脑袋。

### 4.3 Pareto 前沿与实时滑杆

**生成**：用 ε-constraint 方法扫描权重，产生 20–30 个非支配解（省钱型 / 均衡型 / 健康型 / 省事型）。

**交互**：**全部 Pareto 解离线预计算并缓存**，前端滑杆只是查表切换。用户拖动滑杆时响应 < 200ms，**无需重新求解**。

> 这是"演示效果 / 实现成本"比最高的一处：看起来是实时优化，实际是查表，稳、快、不翻车。

### 4.4 中式食材替换图

构建食材替换图 `(缺 A) → (用 B + C 替代)`，例如"没有生抽 → 老抽 + 少许糖"、"没有料酒 → 黄酒 / 米酒"。

**用途**：① 检索召回时放宽约束，提升候选多样性；② Stage 3 中当某食材价格异常或不可得时提供替代方案；③ **本身可作为独立数据集开源**（见 8.3）。

### 4.5 官方价格数据管道与批发-零售折算

**目标**：把"官方公示价格"变成求解器可用的 `p[i]`（食材单价），并保证**成本估算可信**。

**管道四步**

```
① 抓取      定时任务（每日）拉取各平台快照 → 原始层（保留原样，含来源与许可信息）
② 归一化    品名字典 + 单位换算 → 映射到统一食材表 I
            （白菜/大白菜/黄芽白 → 食材ID 1013；  元/公斤 → 元/克）
③ 折算      批发价 × markup(品类) → 零售价估计
            有零售价源时直接使用，并可反向校准 markup
④ 服务      PriceProvider 对外只暴露 p[i]（元/克），带缓存与离线快照
```

**批发 → 零售折算模型（本项目的一个轻量算法点）**

```
p_retail(i, c, d) = p_wholesale(i, c, d) × m(cat(i)) × (1 + ε_i)

其中
  cat(i)    食材品类（叶菜 / 根茎 / 猪肉 / 水产 / 蛋奶 ...）
  m(cat)    品类加价率，初值取经验区间 [1.5, 2.5]
  ε_i       品类内残差，用同时提供零售价源的城市做分位数回归校准
```

> **为什么这是个好的算法点**：它把一个"数据脏"的工程问题变成了可量化、可验证的建模问题 —— 评测中的**成本估算偏差**指标（见 6.1）直接检验它的好坏。而且当多个城市同时提供批发价与零售价时，`m(cat)` 可以用真实数据校准，而不是拍脑袋。

**价格在决策中的三个用法**

| 用法 | 说明 | 落到哪里 |
|---|---|---|
| 目标函数成本项 | `Cost = Σ p[i]·y[i]`，用折算后的零售价 | 4.1 Stage 3 |
| **季节性 / 时令识别** | 价格显著低于历史同期 → 判定为当季，提高推荐权重 | Stage 1 检索 |
| **价格异常触发替换** | 某食材价格飙升 → 经替换图推荐替代品 | 4.4 替换图 |

**时令与替换的联合逻辑（演示亮点）**：
> "本周黄瓜价格是上月的 1.8 倍，已为你换成冬瓜，营养相近，成本低 42%。"

这句话背后是**价格管道 + 替换图 + 求解器**的联合结果 —— 比任何 LLM 现场生成的推荐理由都扎实。

### 4.6 城市路由与三级降级策略 ⭐ v1.3 新增

**先立一条架构红线：网页不能直接调用政府接口。**

用户填完地区后"自动调用"的方向是对的，但**调用对象不是政府平台，而是我们自己的后端**。三个硬性原因：

| 原因 | 说明 |
|---|---|
| **密钥必须保密** | 平台认证需要 `X-Signature`（HmacSHA256 + Secret）。Secret 一旦放进前端 JS 就等于公开泄露 → 必须留在后端 |
| **跨域限制（CORS）** | 政府站点不会为我们的域名放行 CORS，浏览器 `fetch` 会被直接拦截 |
| **配额与合规** | 每次用户操作都实时打政府接口 = 高频访问，既触合规红线，又极易被限流 |

**正确架构：数据同步与数据服务分离**

```
每日定时（离线）                        用户请求（在线）
────────────────────                  ─────────────────────────
定时任务 → 各平台接口                   浏览器：自动定位 / 用户选择城市
        → 原始快照入库                            ↓
        → 归一化 + 批发→零售折算          后端 API：查本地快照库（毫秒级）
        → 生成「城市 × 品类」价格表                ↓
                                        返回：价格 + 地域先验 + 来源标注
```

**关键点：所有支持城市的快照都在每日定时任务中预抓入库。** 用户切换城市时只是**查库**，不是**抓取**。这样一次性拿到：毫秒级响应、不受接口波动影响、断网仍可演示、完全合规。

**两类数据必须分清（常见误解）**

| 数据 | 来源 | 用户选地区后 | 依赖 |
|---|---|---|---|
| **地域菜系先验** | 我们自己手工维护的映射表（几十~几百行），**随代码分发** | 本地查表，**零延迟、零网络请求** | 无 |
| **价格数据** | 官方公示平台 | 查后端本地快照库 | 每日快照任务 |

> ⚠️ **地域偏好不需要调任何政府接口。** 它是一张静态映射表，**断网也能用**。真正需要联网的只有价格。

**三级降级策略（解决"评委问：我们城市能用吗"）**

中国有 300+ 地级市，我们最多深度接入 2–3 个。**如果只支持自己的城市，答辩现场一句"我们这儿能用吗"就会很尴尬。** 所以必须有降级：

```
Tier 1  该城市有本地零售价开放接口
        → 直接使用            标注「本地公示价格」  置信度：高

Tier 2  无本地接口，但同省 / 邻近城市有数据
        → 同省城市均价 + 品类加价率折算
        →                     标注「周边城市参考价」置信度：中

Tier 3  完全无数据
        → 全国批发价均价 × 城市系数（按城市等级 / CPI 粗调）
        →                     标注「全国均价估算」  置信度：低
```

**UI 必须诚实标注来源与置信度**，例如价格旁一个可点击的小标签：

```
黄瓜  ¥5.2/斤   ⓘ 本地公示价格 · 更新于 2026-09-15
土豆  ¥2.8/斤   ⓘ 周边城市参考价 · 置信度中
```

> **这既是对用户的诚信，也是答辩加分项** —— 它证明我们清楚自己数据的边界，而不是假装全国都有精确数据。评委对"知道自己局限"的队伍印象通常更好。

**可以做的自动化亮点**

| 自动化 | 实现 | 成本 |
|---|---|---|
| **城市自动预填** | 浏览器 Geolocation API 或后端按 IP 粗定位，预填城市，用户可改 | 0.5 人日 |
| **城市名自动补全** | 输入前几个字 → 下拉候选（本地城市表，无需联网） | 0.5 人日 |
| **数据源自动路由** | 选定城市 → 后端自动匹配适配器 + 菜系先验 + 当季规则 | 已在管道内 |
| **数据新鲜度提示** | 首页显示"价格数据更新于 X"，过期时标黄 | 0.5 人日 |

**答辩演示的额外好处**：因为走的是本地快照，现场可以放心演示"切换到成都 → 价格立刻变" —— **视觉效果与实时调用完全一样**，但不会因为政府接口慢或挂掉而翻车，还能顺手展示溯源标签，显得更专业。

**这一节也让开源工具包的定位更清楚了**：它交付的不是"一个抓取脚本"，而是**一个可直接部署的「中国城市农产品价格服务」** —— 含适配器、归一化、折算、城市路由与降级。这比脚本有价值得多（见 8.3）。

### 5.1 官方农产品价格数据源（已核实）⭐

> 本节是对 v1.0 的重要升级：价格数据从"自采集样本"改为"**官方公示数据**"，评测可信度由此质变。

**数据源全景**

| 数据源 | 层级 | 价格类型 | 接入方式 | 状态 |
|---|---|---|---|---|
| **农业农村部「全国农产品批发市场价格信息系统」** `pfsc.agri.cn` | 国家级 | **批发价**（元/公斤，日频） | 网页查询，未见官方开放 API | 权威性最高，需评估合规接入方式 |
| **省市公共数据开放平台**（山东、成都、凉山、金华、深圳、无锡…） | 省 / 市级 | **零售价**（成都：中心城区农贸市场主副食品；凉山：全州农副产品市场零售价）或指数 | **标准 REST API**，注册申请 Client-Id / Secret | ✅ **已核实存在，推荐主用** |
| 地方「菜篮子」价格指数 / 平价商店公示 | 市级 | 指数或零售价 | 网页 / API | 备选 |

**关键工程洞察：省市公共数据开放平台采用统一的网关认证规范** —— `X-Client-Id` + `X-Timestamp` + `X-Nonce` + `X-Signature`（HmacSHA256 → Base64），分页参数为 `OFFSET/LIMIT` 或 `ROWNUM/PAGESIZE`。

> **这意味着写一个通用客户端就能同时接入多个平台，边际成本极低。** 这也是我们开源工具包能成立的技术基础。

**已核实的具体接口（示例）**

- **凉山州「全州农副产品市场零售（成交）价格表查询接口」** — `https://data.lszdsjzx.cn/gateway/api/1/swj_qznfcpsclscjjgb`｜GET｜**无条件开放**｜来源：州商务局
  - ⚠️ 返回字段为拼音缩写（`zrby / zrtq / nrby / nrtq / jdby / jdtq / dmby ...`，推测为"品类 + 本月/同期"），**需人工建立字段字典** —— 这本身就是一项有价值的开源贡献
- **山东「菜篮子数据集分页查询服务」** — `https://data.sd.gov.cn/gateway/api/1/uploadfarmgoodprice`｜**无条件开放**｜来源：泰安市发改委
  - 返回字段规范：`farmproduce_name` / `farmpricedaily_price` / `farmmark_name` / `farmmark_adress` / `farmproduce_classname`
- **成都「中心城区部分农贸市场主副食品价格信息接口」** — 成都市公共数据开放网｜**零售价，与家庭买菜场景最贴合**
- **金华「金华市区菜篮子价格指数信息」** — `interface/gateway.do`｜月频｜**指数而非单品价**，仅可用于趋势 / 通胀调整
- **农业农村部「全国农产品批发市场价格信息系统」** — `https://pfsc.agri.cn/`｜批发价原始来源

**选源建议：不要贪多。** 选 **1 个团队所在城市**（可实地核对价格，直接验证折算模型）+ **1 个数据开放的对比城市**，做深度接入即可。

**⚠️ 八条必须提前处理的坑**

| # | 坑 | 后果 | 应对 |
|---|---|---|---|
| 1 | **批发价 ≠ 零售价**。家庭买菜是零售，通常是批发的 **1.5–2.5 倍** | 不做折算 → 成本严重偏低、评测失真 | 建**品类级加价率模型**（见 4.5），用零售价源校准 |
| 2 | **口径单位不统一**：元/公斤 vs 元/500g vs 元/斤；品名不统一（白菜/大白菜/黄芽白；土豆/马铃薯/洋芋） | 数据无法直接使用 | 建**品名归一化字典**映射到食材表 |
| 3 | **地区差异巨大**：全国 4000+ 批发市场，城市间零售价差异显著 | 全国覆盖不现实 | 限定 2–3 个代表城市，不追求全国 |
| 4 | **接口需申请令牌且有配额**，注册 + 申请 + 写对 HmacSHA256 签名都要时间 | 外部依赖卡住 W2 | **W1 第一天就启动申请** |
| 5 | **绝不高频爬取政府网站**（合规红线） | 违规 + 被封 | **每日定时抓取一次快照入库**，应用只读本地库 |
| 6 | **答辩现场断网 / 接口限流** | demo 直接翻车 | **演示全程走本地快照**，绝不在现场实时调用政府接口 |
| 7 | **许可与再分发**：每个数据集有独立「数据使用许可」 | 开源合规风险 | **可再分发的才随仓库开源；不可再分发的只开源字段字典与抓取脚本，原始数据不入库** |
| 8 | **历史序列只能自己攒**：官方平台多只提供最新快照 | 无法做真实价格回测 | **W1 启动每日快照任务**，一个月自然积累 30+ 天序列 |

> **架构红线**：以上数据**不能由网页直接调用**（密钥泄露 + CORS + 配额合规），必须经后端每日快照中转 —— 详见 4.6。

**这一节反而强化了开源故事**：品名归一化字典 + 拼音字段字典 + 批发零售折算模型 + 统一网关客户端，是一套**别人能直接拿去用的通用工具** —— 比再写一个 App 有价值得多（见 8.3）。

**合规底线（写作与答辩时必须明确声明）**：
- 不抓取电商平台受保护数据；不使用绕过反爬手段；遵守目标平台 `robots.txt` 与「数据使用许可」
- 所有数据来源在 `docs/dataset-card.md` 中逐条列明来源部门、开放属性、许可与获取时间
- 对用户展示的价格标注"数据来源：XX 平台公示价格（更新于 YYYY-MM-DD）"

**合成家庭生成器**参数维度：
```
人数 1–5 | 周预算 150–800 元 | 慢病 {无, 高血压, 糖尿病, 高血脂}
口味 {嗜辣, 清淡, 重口, 均衡} | 过敏原 {无, 海鲜, 花生, 乳制品, 麸质}
地域 {川, 粤, 鲁, 苏, 湘, 东北, 西北, 江浙, 云贵}    ← v1.2 新增，驱动地域先验
厨具 {仅炒锅, 炒锅+电饭煲, 全厨具} | 加班日数 0–3 | 是否接受剩菜
```
采样 30 个家庭 + 3 个手工设计的极端案例（如"1 人 / 200 元 / 糖尿病 / 只吃清真 / 只有一口锅 / 每天加班"）。

**⚠️ v1.2 调整：仿真周期从 1 周扩展为 4–8 周。** 记忆与偏好学习的效果在单周内**不可观测**，必须多周仿真才能测出学习曲线（见 6.3）。

## 6. 评测方案（拿奖关键）

> **评测必须从 W1 就开始搭框架**，与算法并行推进。最后一周才做评测的队伍通常交不出表。

### 6.1 指标定义

| 指标 | 定义 | 方向 | 备注 |
|---|---|---|---|
| 营养达标率 | 热量/蛋白/蔬菜/钠 四项均达标的天数占比 | ↑ | 核心健康指标 |
| 日均成本 | 元 / 人 / 天 | ↓ | 核心经济指标（基于官方公示价格） |
| **成本估算偏差** | 预估采购成本 vs 真实结算价的平均相对误差 | ↓ | **新增**：检验批发→零售折算模型（见 4.5） |
| **价格响应正确率** | 价格上涨时应替换、且实际正确替换的比例 | ↑ | **新增**：检验价格异常触发逻辑 |
| **食材浪费率** | 浪费量 / 采购量 | ↓ | **本项目主攻指标** |
| 偏好满足度 | nDCG@7（vs 模拟用户真实偏好） | ↑ | 体验指标 |
| 菜单多样性 | 7 天内不同食材数、不同菜系数 | ↑ | 防塌缩 |
| **安全违规数** | 过敏/禁忌/钠超标次数 | **必须 = 0** | 一票否决 |
| 求解耗时 | 端到端秒数 | ↓ | 工程指标 |
| LLM 成本 | 元 / 家庭 / 周 | ↓ | 落地可行性 |
| 模拟接受率 | 模拟用户接受推荐菜品的比例 | ↑ | 综合体验 |
| **地域契合度** | 推荐菜系分布 vs 地域先验分布的余弦相似度 | ↑ | **v1.2 新增** |
| **冷启动表现** | 第 1–3 天的偏好满足度（此时没有任何个人历史） | ↑ | **v1.2 新增**：检验地域先验的价值 |
| **菜品重复率** | 相邻两周重复菜品的比例 | ↓ | **v1.2 新增**：检验记忆的重复惩罚 |
| **学习曲线斜率** | 周接受率随周数上升的斜率 | ↑ | **v1.2 新增**：证明记忆推荐真的在学 |

### 6.2 Baseline 阶梯与消融实验

**Baseline 阶梯**（每加一层即可量化该层的贡献）：

```
B0  随机菜单                                   （下界）
B1  规则模板（按菜系轮换 + 固定搭配）
B2  单 Agent LLM 直接生成菜单                    （最常见的"套壳"方案）
B3  多 Agent 流水线，但不用求解器（LLM 协商）
B4  多 Agent + CP-SAT 求解器          ← 我们
B5  B4 + 基础在线偏好学习
B6  B5 + 地域先验 + 跨周记忆（含时间衰减）   ← v1.2 主推组合
B7  B6 + 不确定性/鲁棒优化（如有时间）
```

**消融实验**（证明每个模块都必要）：

```
A1  去掉保质期项（Waste 权重置 0）        → 观察浪费率上升
A2  去掉 Critic 否决                     → 观察安全违规数上升（应显著劣化）
A3  去掉 Pareto，只输出单解               → 观察偏好满足度下降
A4  去掉食材替换图                       → 观察多样性下降
A5  固定随机种子复跑 5 次                 → 观察稳定性（方差）
A6  去掉地域先验                         → 观察冷启动期（第 1 周）偏好满足度下降
A7  去掉跨周记忆 / 时间衰减               → 观察学习曲线是否变平、重复率是否上升
A8  时间衰减半衰期扫描（1 / 2 / 4 / 8 周） → 选出最优 λ，讲清"记忆该记多久"
```

### 6.3 模拟用户模型与多周仿真（v1.2 升级）

不依赖真人，用概率模型模拟反馈：

```
P(接受菜 r | ctx) = softmax( pref(u, r, ctx, t) / τ )
```

> **⚠️ v1.2 关键调整：仿真必须从 1 周扩展到 4–8 周。**
> 记忆推荐与偏好学习的效果**在单周内不可观测** —— 单周仿真下 B5 / B6 与 B4 的差异会淹没在噪声里。只有多周仿真才能测出"越用越准"，这也是本方案最有力的一份证据。
并在部分家庭中加入"心情扰动"（随机波动），测试方案鲁棒性。

### 6.4 结果呈现

- 主表：30 个合成家庭 × 7 个 baseline × 13 个指标的均值 ± 标准差（多周 × 多种子）
- 图表：浪费率随家庭预算变化曲线、Pareto 前沿散点、消融对比条形图
- **学习曲线（v1.2 主推图）**：周接受率随周数变化，例如 W1 52% → W2 61% → W3 70% → W4 78%
- 一键复现：`make eval` 输出全部表格与图表

## 7. 前端与交互设计

### 7.1 技术选型【冻结】

| 项 | 选型 | 说明 |
|---|---|---|
| 框架 | React 18 + Vite + TypeScript | 产品感强，AI 结对开发效率高 |
| 样式 | Tailwind CSS | 快速出效果，无需设计基础 |
| 组件 | shadcn/ui 或 Ant Design Mobile | 直接可用的成品组件 |
| 状态 | Zustand（轻量） | 新手友好，避免 Redux 复杂度 |
| 图表 | Recharts / ECharts | Pareto 散点、营养雷达图 |
| PWA | vite-plugin-pwa | 一键生成 manifest + Service Worker |

**开发方式**：前端代码由 AI 结对生成，团队成员负责**设计、验收与联调**。这弥补新手在工程细节上的经验缺口。

### 7.2 核心页面

1. **首页 / 家庭设置**：人数、预算、慢病、过敏、厨具、每日时间、**地域**（v1.3：自动定位预填 + 城市名补全 + 手动覆盖；滑杆 + 勾选，无需打字）
2. **主决策页**（答辩主战场）
   - 七日菜单卡片（可拖动替换）
   - 右侧**权衡滑杆**：省钱 ↔ 健康 ↔ 省事 —— 拖动即重排菜单
   - 底部**采购清单**：按"蔬菜 / 肉禽蛋 / 调味 / 主食"分类，带总价
   - 每次替换弹出**解释气泡**："换成这道菜后钠仍达标，且能消耗周三即将过期的菠菜"
   - **价格提醒条**："本周黄瓜涨至 8.6 元/斤（+38%），已推荐冬瓜替代" —— 每项价格带**来源与置信度标签**（本地公示 / 周边参考 / 全国估算），可点击溯源（见 4.6）
3. **协作轨迹页**（体现"多智能体"）
   - 时间轴展示各 Agent 的输入输出、Critic 是否否决及原因
   - 这是让评委"看见"多智能体的关键页面
4. **评测页**：benchmark 表格与消融图（可直接投影给评委看）
5. **记忆与偏好页**（v1.2 新增，答辩第二亮点）
   - **记忆时间轴**：过去几周采纳 / 拒绝了哪些方案、当时的反馈与上下文
   - **偏好画像**：口味雷达图，**地域先验 vs 个人调整后**对比显示
   - **为什么我记得**：点击任一偏好项，展开是哪几次反馈形成的（可解释性）
   - 隐私开关：一键清空本地记忆

### 7.3 演示脚本（3 分钟）

[0:00] 输入："三口之家，周预算 300 元，妈妈高血压，孩子不吃辣，

### 8.2 可复现性（评委最看重）

- **一键启动**：`docker compose up` → 前后端齐活；`.env.example` 提供全部配置项
- **一键评测**：`make eval` → 输出全部表格与图表到 `benchmarks/results/`
- **依赖锁定**：`requirements.txt` / `pnpm-lock.yaml` 固定版本
- **数据随仓库分发**：核心数据表入库（体积可控），确保离线可跑
- **无 API Key 降级模式**：`MOCK_LLM=1` 时用规则模拟 LLM，**评委无需付费即可复现全流程** ← 重要加分点

### 8.3 反哺开源生态（"开源赛道"最强故事）

不只"使用开源"，而是**回馈开源**，五个候选方向（按性价比排序）：

1. **「中国城市农产品价格服务」开源工具包** ⭐ 性价比最高 —— 统一网关客户端（多平台通用签名认证）+ 品名归一化字典 + 拼音字段字典 + 批发→零售折算模型 + **城市路由与三级降级**（见 4.6）。交付的不是抓取脚本，而是一个**可直接部署的服务**；做菜谱 / 生鲜 / 营养 / 价格分析类项目的人会真正需要它，且我们已核实多个省份开放平台存在同类接口
2. **中式食材替换知识图谱数据集**（80–150 条规则）→ 独立开源，配数据集卡。小而完整，易被引用
3. **家庭饮食决策评测基准 MealBench**（合成家庭生成器 + 评测脚本）→ 让其他团队/研究者可复用与对比
4. **地域→菜系偏好映射表 + 偏好建模参考实现**（v1.2 新增）→ 30–40 个地区的菜系权重先验，可被推荐系统 / 饮食研究直接复用
5. **向 HowToCook 等上游项目提交 PR** → 补充菜谱结构化字段或食材分类，留下公开贡献记录

> 答辩时可以说："我们不仅用了开源，还向社区回馈了 X 和 Y，目前已有 N 次下载 / M 个 star / 被上游合并 K 个 PR。"

## 9. 排期与分工

### 9.1 四周排期

| 周 | 里程碑 | 具体任务 | 验收标准 |

| **W2** | **核心算法跑通** | CP-SAT Stage 2 菜单求解、Stage 3 采购批量优化、保质期浪费最小化、**价格管道：归一化 + 折算 + 城市路由与三级降级上线** | 30 个合成家庭跑出 B4 完整指标；成本估算偏差 < 15% |
| **W3** | 多智能体 + 体验 | Critic 否决机制、**统一偏好状态模型（地域先验 + 跨周记忆 + 时间衰减）**、Pareto 集生成、前端主决策页、协作轨迹页、**记忆与偏好页** | 端到端可用，滑杆响应 < 200ms；多周仿真跑出学习曲线 |
| **W4** | 收尾冲刺 | 消融实验 A1–A8、评测页、Docker 打包验证、文档补全、中英 README、演示视频、技术报告 | 他人可在干净机器上 `docker compose up` 成功复现 |

**关键提醒**：
- **外部依赖第一天就启动**：数据开放平台令牌申请有等待周期，晚一周申请就可能赶不上 W2 的价格管道
- **价格快照任务 W1 就要跑起来** —— 历史序列只能靠自己逐日积累，越早开始越好
- **评测从 W1 开始**，不要留到最后
- **W2 结束必须有数字**，否则 W4 一定交不出消融表
- **多周仿真的框架必须在 W2 定下来**（4–8 周），否则 W4 无法证明记忆功能有效
- **W4 前 3 天冻结功能**，只修 bug 与写文档

## 10. 风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|---|---|---|---|
| **变成"套壳 Chatbot"** | 高 | 致命 | 求解器 + 消融表兜住；所有硬约束走确定性代码 |
| **新手进度不及预期** | 高 | 高 | 技术栈压到最简；W1 只做骨架与数据；砍 Later 项 |
| **官方价格接口申请不下来 / 限流** | 中 | 中 | 同时申请 2–3 个平台；保留自采集样本兜底；应用只读本地快照，不受接口波动影响 |
| **批发→零售折算不准导致成本失真** | 中 | 高 | 用有零售价源的城市校准 markup；评测中设"成本估算偏差"指标把关 |
| **答辩现场断网 / 接口被限流** | 中 | **致命** | **演示全程走本地快照，绝不实时调用政府接口**；准备离线模式开关 |
| 价格数据许可不允许再分发 | 中 | 中 | 只开源字段字典、归一化表与抓取脚本，原始数据不入库 |
| 品名归一化工作量大 | 高 | 中 | 先覆盖 60–120 个高频食材（约覆盖 80% 采购量），长尾后补 |
| **用户城市未被数据覆盖** | **高** | 中 | **三级降级策略（见 4.6）**：本地公示 → 周边参考 → 全国估算，UI 诚实标注置信度 |
| 前端误直连政府接口 | 中 | 中 | 架构红线：密钥与签名只在后端；前端只调自家 API；Code Review 把关 |
