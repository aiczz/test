# 接口契约 · 三餐智囊（前端 ↔ 后端）

> **这份文件是给前端和后端一起看的「合同」。**
> 前端负责人：__（你）  后端负责人：__
> 版本：v1.0 · 2026-09-15
>
> **一句话**：前端按这份格式把界面全部做完，后端按这份格式返回数据。**谁都不能单方面改字段名**，要改必须先通知对方。

---

## 0. 为什么要先定这个

前端和后端是两个程序，靠网络"对话"。对话格式必须先约好，否则：

```
前端以为字段叫  dishName
后端返回的是    dish_name
→ 页面白屏，报错「Cannot read properties of null」
→ 查两小时，发现是一个下划线的问题
```

**定下契约还有两个好处：**

1. **前端可以立刻开工** —— 用假数据把界面全做完，不等后端
2. **后端可以放心实现** —— 不用猜前端要什么字段

---

## 1. 主接口：获取一周方案

```http
GET /api/plan?user_id={user_id}&week={week}
```

| 参数 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `user_id` | string | 是 | 用户标识（前端本地生成，不是手机号） | `u01` |
| `week` | string | 是 | ISO 周格式 `YYYY-Www` | `2026-W38` |

**成功响应**：`200`，返回下面的 JSON。

---

## 2. 响应 JSON 完整结构

```jsonc
{
  // ---------- 元信息 ----------
  "meta": {
    "generated_at": "2026-09-14T21:30:00",   // 生成时间
    "price_data_date": "2026-09-14",         // 价格数据日期（前端显示"数据更新于 X"）
    "price_city": "成都",                    // 价格所属城市
    "solve_ms": 1840,                        // 求解耗时（毫秒）
    "solver": "CP-SAT"                       // 求解器名称
  },

  // ---------- 周概览 ----------
  "week": "2026-W38",
  "budget": 300,          // 用户设定的周预算（元）
  "total_cost": 296.0,    // 实际采购总成本（元）
                          // ⚠️ 必须等于 shopping_list 里所有 price 的累加和

  // ---------- 营养汇总（前端画雷达图用）----------
  "nutrition": {
    "calories_per_person_per_day": 1980,
    "protein_g_per_person_per_day": 68,
    "vegetable_g_per_person_per_day": 412,
    "sodium_mg_per_person_per_day": 1720,
    "sodium_limit_mg_per_person_per_day": 2000   // 用于画"钠摄入 / 上限"进度条
  },

  // ---------- 七日菜单 ----------
  "days": [
    {
      "date": "2026-09-15",       // YYYY-MM-DD
      "weekday": "周一",           // 中文，前端直接显示
      "meals": [
        {
          "slot": "breakfast",    // 枚举：breakfast | lunch | dinner
          "dishes": [
            {
              "id": 2001,                  // 菜品 ID（整数，菜谱库主键）
              "name": "小米粥",             // 菜品名
              "servings": 3,               // 份数（整数）
              "reason": "温和易消化，适合全家",  // ★ 推荐理由，前端在卡片上显示
              "tags": ["快手", "清淡"]       // 标签数组，可为空数组 []
            }
          ]
        }
      ]
    }
    // ... 共 7 个元素
  ],

  // ---------- 采购清单 ----------
  "shopping_list": [
    {
      "category": "蔬菜",              // 分类名，前端做分组标题
      "items": [
        {
          "name": "番茄",              // 食材名
          "amount": 500,               // 数量（数字）
          "unit": "g",                 // 单位：g | kg | 个 | 盒 | 瓶 | L | 份
          "price": 5.2,                // ★ 该项小计金额（元），不是单价
          "price_source": "local"      // 枚举，见下表
        }
      ]
    }
    // ... 建议 4–6 个分类
  ]
}
```

### `price_source` 枚举（价格来源，前端显示成小标签）

| 值 | 前端显示 | 含义 | 置信度 |
|---|---|---|---|
| `local` | 本地公示价格 | 该城市有官方开放接口，直接用 | 高 |
| `nearby` | 周边城市参考价 | 同省/邻近城市均价折算 | 中 |
| `national` | 全国均价估算 | 全国批发均价 × 城市系数 | 低 |

> ⚠️ **只能返回这三个值。** 前端会按这三个值显示不同的标签颜色。

## 3. 错误响应格式（统一）

无论什么错误，都返回这个结构，前端才能给用户友好提示：

```jsonc
{
  "error": {
    "code": "INFEASIBLE",                                  // 错误码，见下
    "message": "当前预算下无法同时满足营养与忌口要求",       // 给用户看的中文
    "binding_constraint": "budget"                         // 可选：哪条约束最紧
  }
}
```

| `code` | HTTP | 场景 |
|---|---|---|
| `INVALID_PARAM` | 400 | 参数缺失或格式错 |
| `NO_SUCH_USER` | 404 | user_id 不存在 |
| `INFEASIBLE` | 409 | **求解器无解**（约束冲突）——前端会提示用户放宽哪条约束 |
| `PRICE_UNAVAILABLE` | 503 | 价格数据暂不可用 |
| `INTERNAL` | 500 | 其他 |

## 4. 第二阶段接口：记录用户反馈（暂不急，先知道有这回事）

用户点「不想吃这道」或「实际做了」时上报，用于记忆推荐。

```http
POST /api/feedback
Content-Type: application/json

{
  "user_id": "u01",
  "dish_id": 1042,
  "action": "rejected",              // 枚举：adopted | rejected | replaced | cooked | skipped
  "reason": "too_spicy",             // 可选，用户选的原因标签
  "context": { "dow": 1, "overtime": true },   // 可选
  "ts": "2026-09-16T19:20:00"
}
```

响应：`200 {"ok": true}`

> 这个接口**可以最后做**，前端会先把 UI 做好但不上报。

## 5. 约定（这些细节最容易出问题）

| 项 | 约定 |
|---|---|
| **字符编码** | 一律 **UTF-8**（后端注意设置 `Content-Type: application/json; charset=utf-8`） |
| **时间格式** | ISO 8601：`2026-09-15T21:30:00`，不带时区 |
| **日期格式** | `YYYY-MM-DD` |
| **周格式** | `YYYY-Www`（如 `2026-W38`，周数补零） |
| **金额** | 数字类型，单位**元**，保留 1–2 位小数。**不要返回字符串 `"5.2"`** |
| **`amount`** | 数字类型。**不要返回字符串 `"500"`** |
| **`price` 的含义** | **该项小计**（不是单价）。单价 = `price ÷ amount`（单位一致时） |
| **`servings`** | 整数，指"几人份" |
| **空数组** | `tags` 没有就给 `[]`，**不要给 `null`** |
| **字段缺失** | 契约里有的字段**必须返回**，哪怕是空数组。不要省略 |
| **分页** | 一期不用 |

## 6. 完整样例文件

完整的、可解析的示例在这里（7 天 / 6 个分类 / 29 个条目，金额已自洽）：

```
mock/plan.json
```

**后端同学可以直接把它当作"期望输出"的参照**，甚至有它就能先写一个假接口，让前端先联调。

**前端同学把它复制到 Flutter 项目里当假数据用：**

```bash
# 创建 Flutter 项目之后
mkdir -p mealmind/assets/mock
cp mock/plan.json mealmind/assets/mock/plan.json
```

然后在 `pubspec.yaml` 里声明：

```yaml
flutter:
  assets:
    - assets/mock/
```

## 7. 变更流程（重要）

> **字段名一旦定了就不改。** 实在要改，必须：

1. 先在群里说清楚：改哪个字段、为什么、改成什么
2. **双方都确认**之后才动手
3. 改完同步更新**这份文件**和 `mock/plan.json`
4. 前端 `USE_MOCK` 开关翻过来联调

**禁止**：后端悄悄把 `dish_name` 改成 `dishName`，或者把 `price` 从数字改成字符串。
