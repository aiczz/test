# 决策备忘：微信小程序 vs PWA（交付形态）

> **日期**：2026-09-15
> **背景**：团队提出用微信小程序替代原生 App 作为交付形态，需评估可行性
> **结论**：**可以做，但不能作为主交付，也不能进关键路径。** 有一个决定性障碍：**算法备案周期 2–4 个月 > 你们 1 个月的总工期**。
> **建议**：**PWA 为主交付（保命 + 开源可复现），小程序为加分形态（用 Taro 一套代码多端产出）**

---

## 一、决定性障碍：算法备案

这是评估中最关键的发现，直接决定"能不能上线"。

### 1.1 法律依据（三部法规同时命中）

| 法规 | 与本项目的关系 |
|---|---|
| 《互联网信息服务算法推荐管理规定》 | 我们的**菜品排序推荐**、**个性化偏好学习**命中「排序精选」「个性化推送」 |
| 《互联网信息服务深度合成管理规定》 | 我们用 LLM **生成菜单与做法**命中「生成合成（深度合成）」 |
| 《生成式人工智能服务管理暂行办法》 | 调用大模型提供服务，在此办法管辖范围内 |

**备案范围明确包含「小程序」**，与 APP、网站、公众号并列。

### 1.2 我们命中三类算法备案

| 类型 | 我们的功能 |
|---|---|
| 生成合成（深度合成） | LLM 生成菜单、烹饪步骤、推荐理由 |
| 个性化推送 | 偏好学习、跨周记忆、地域先验 |
| 排序精选 | 菜品排序与推荐分计算 |

**三类全中。** 这不是可以回避的边角问题。

### 1.3 周期与后果

```
主体备案（初审）      约 7–10 个工作日
算法信息填报（复审）   + 产品信息补充
网信办分批公示        需等批次
────────────────────────────────
整体周期              约 2–4 个月
```

**⚠️ 2–4 个月 > 你们的总工期 1 个月。** 正式发布这条路在时间上就是不通的。

未备案的后果（如果强行发布）：应用商店/微信审核不通过、已上线强制下架、行政罚款 1 万–10 万元。

### 1.4 备案材料需要企业主体

营业执照、法定代表人身份证、**算法安全负责人**身份证及工作证明、《算法安全自我评估报告》、《算法承诺书》等。

> 学生团队通常没有企业主体。这一条本身就构成硬门槛。

### 1.5 ✅ 但有一个重要出口：**不上架就不触发**

**关键区分**：

| 形态 | 是否需要 ICP 备案 | 是否需要算法备案 | 可用性 |
|---|---|---|---|
| **开发版** | 否 | 否 | 只有开发者本人能用 |
| **体验版** | 否 | 否 | 可加**体验成员**（上限约 100 人），生成体验版二维码 |
| **正式发布** | 是 | 是（2–4 个月） | 公众可用 |

**结论**：如果只在**体验版**范围内演示（把评委/老师加为体验成员），**技术上完全可行，不需要备案**。

但这立刻带来下一个问题 → 见第三节。

## 二、好消息：类目不是问题

查了微信官方《小程序备案服务内容标识选择指引》，我们的功能**个人主体可以合规选择**：

| 可选类目 | 释义 | 个人备案 |
|---|---|---|
| **咨询广场** | 「适用于提供娱乐、服饰、美妆、科普、养生、法律、求职、拍卖、体育、旅游、科技、**美食**等行业资讯信息」 | ✅ 可选，符合个人性质 |
| **工具 → 报价/比价** | 「适用于提供商品价格展示/价格对比等服务」 | ✅ 可选，符合个人性质 |
| **工具 → 健康管理** | 「适用于记录/测试与健康相关内容，如身高、体重、个人身体管理记录等服务」 | ✅ 可选，符合个人性质 |

**推荐选「咨询广场」（美食资讯）**，与我们"饮食推荐"的定位最贴。

**注意避免**（个人主体不建议/不可选）：餐饮-点餐、餐饮-外卖、批发和零售业-零售批发、自主售卖。
→ 也就是**不能做交易闭环**，只做推荐与展示。我们本来也不做交易，没问题。

## 三、真正的问题：不是合规，是这三条

合规问题有出口（体验版），但下面三条是**实打实的代价**：

### 3.1 ⚠️ 最致命：小程序直接打击开源赛道的「可复现性」

这是我要重点强调的一条。

- **PWA**：评委 `git clone` → `npm install` → `npm run dev` → **浏览器直接打开看**。零门槛。
- **小程序**：评委需要**微信开发者工具 + 一个 AppID** 才能运行。**没有 AppID 就完全跑不起来。**

`项目方案.md` §8.2 把「可复现性」列为"评委最看重"的一项。小程序源码开源后，别人 fork 了也跑不动 —— **开源交付的意义被大幅削弱**。

> 对"AI+开源赛道"，这一条的权重可能高于"形态是否像 App"。

### 3.2 新技术栈 + 微信开发者工具 = 新手的时间黑洞

- 小程序用 **WXML / WXSS / JS**，不是标准 HTML/CSS
- 必须用**微信开发者工具**，真机预览要扫码，调试体验远不如浏览器 DevTools
- 多端适配有大量小坑（组件差异、API 差异、样式单位 rpx）

对"新手为主 + 1 个月"的团队，这是高风险投入。

### 3.3 演示形态受限于体验成员

- 体验版二维码需要把使用者**加为体验成员**（有数量上限）
- **评委不可能都被你们加进去**
- 现场大概率还是**你们自己的手机 + 投屏**演示 —— 那么 PWA 和小程序的演示效果**没有区别**

## 四、三种形态的完整对比

| 维度 | PWA（响应式 Web） | 微信小程序 | 原生 App |
|---|---|---|---|
| 开发成本 | **1×** | 1.5–2× | 2.5–3× |
| 新技术栈学习 | 无（标准 Web） | 有（WXML/WXSS + 开发者工具） | 有（Flutter/RN） |
| 浏览器可直接运行 | ✅ **是** | ❌ 否 | ❌ 否 |
| **开源可复现性** | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐ |
| 正式发布审批 | 域名 ICP 备案 | ICP + **算法备案 2–4 个月** | 应用商店审核 + 备案 |
| 体验版/开发版可用 | ✅ | ✅（需加体验成员） | 需签名安装 |
| 手机观感 | ⭐⭐⭐⭐（可加到主屏、全屏无浏览器栏） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 场景贴合度（买菜） | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 答辩演示可控性 | ⭐⭐⭐⭐⭐（断网也能演示） | ⭐⭐⭐（依赖微信环境） | ⭐⭐⭐ |
| 时间风险 | **低** | 中–高 | 高 |

## 五、推荐方案：一份代码，两种形态

### 5.1 技术路径

用 **Taro（React 语法）** 一套代码，同时编译出 **H5（PWA）** 和 **微信小程序**。

- Taro 支持 **React + TypeScript**，与我们已定的 React 选型兼容（不是换技术栈，是加一个编译目标）
- 产出：同一套页面逻辑 → H5 版本 + 小程序版本

### 5.2 但务必遵守的风险控制原则

> **小程序绝不进关键路径。**

| 阶段 | 任务 |
|---|---|
| **W1（今天就做）** | ① **注册小程序个人主体 + 拿 AppID**（外部依赖，有等待周期）② 主交付仍按 **PWA** 推进 |
| **W1–W3** | 全力做 **PWA 主交付** + 算法 + 评测（关键路径，必须稳） |
| **W4** | 用 Taro 编译出**小程序体验版**，作为加分形态提交。<br>**有余力就做，做不完就砍 —— 不影响主交付。** |

### 5.3 保底方案（如果 W4 时间不够）

小程序端只做一个**极简壳**：用 `<web-view>` 组件加载你们的 H5 页面。

⚠️ 但这需要配置**业务域名**，而业务域名要求**已完成 ICP 备案的域名**（个人可备案，周期约 7–20 个工作日）—— **这同样是一条外部依赖，必须 W1 就启动**。

---

## 六、我的建议（一句话）

> **主交付用 PWA，小程序用 Taro 作为"如果来得及就加"的加分形态。**
>
> **答辩现场用手机浏览器打开 PWA 并「添加到主屏幕」—— 全屏、无浏览器栏、有图标，观感与小程序几乎无差别，且零审批依赖、断网也能演示。**

把省下来的时间投到**求解器 + 评测 + 消融实验**上 —— 那才是"AI 算法精英大赛"和"开源赛道"真正给分的地方。

## 七、待确认（决定成本结构的关键信息）

| # | 事项 | 为什么关键 |
|---|---|---|
| 1 | **队友里有人会小程序开发吗？** | 如果**已经会**，成本结构完全不同，可以直接上 Taro 甚至原生小程序 |
| 2 | **有没有可用的 AppID？**（个人主体 / 学校企业主体） | 决定体验版能否产出 |
| 3 | 学校/学院能否提供**企业主体资质**？ | 若有企业主体，备案路径会更顺（但仍受 2–4 个月周期限制） |
| 4 | 是否有**已 ICP 备案的域名**可用？ | 决定 `<web-view>` 壳方案是否可行 |
